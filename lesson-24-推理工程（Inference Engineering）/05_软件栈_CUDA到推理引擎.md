## 0. 为什么软件层这么重要（作者的立论）

> **"NVIDIA 在推理市场的统治地位，很大程度上归功于其硬件周围健壮而成熟的软件生态。"**

一条很硬的对比：

| | 迭代周期 |
|---|---|
| **硬件** | 慢——**Apple 和 NVIDIA 这类顶级公司最多一年一代，两年更常见** |
| **软件** | 快——**为了 day-zero 跑新模型，常常要装每个依赖的 nightly 构建** |

**推论**：**软件的快速迭代和低门槛，极大扩展了推理工程的版图**——硬件圈中心是 NVIDIA 和几个竞争者，**而软件层有无数公司在各层堆栈上作业**。

**四个关键玩家**：

| 玩家 | 提供什么 |
|---|---|
| **NVIDIA** | 自己的（有时闭源的）软件生态，从 CUDA 到 Dynamo |
| **Hugging Face** | 所有开放模型的 registry + transformers/diffusers |
| **Linux Foundation** | 硬件无关的项目：**PyTorch、vLLM** |
| **LMSYS Org** | **SGLang** 等推理与评测工具 |

**本章的组织逻辑（按抽象层次递进）**：

```
CUDA            直接和 GPU 通信，显式控制计算与内存
  ↓
深度学习框架     在 CUDA 之上的抽象，用 Python 训练/导出/运行
  ↓
推理引擎         高度可配置的、PyTorch 支撑的常见架构推理
  ↓
NVIDIA Dynamo   坐在推理引擎之上，支撑大规模部署
```

**作者的一句总纲**（很实用）：

> **"今天大多数推理工程发生在较高的抽象层——配置和部署推理引擎、编排多 GPU 推理。但无论你在哪一层工作，对相邻抽象层有强心智模型都是必需的。"**

## 1. CUDA

### 1.1 四个组件

| 组件 | 说明 |
|---|---|
| **CUDA kernel** | **在 GPU 上执行并行代码的用户定义函数** |
| **CUDA graph** | kernel 和其他 GPU 操作的 **DAG**，用于优化重复流程 |
| **CUDA driver** | 应用与 GPU 之间的**底层接口**，管理内存与执行 |
| **CUDA runtime** | **面向开发者的 API**，启动 kernel、管理内存 |

**两个定义上的澄清**（作者特意强调）：

$$ \text{CUDA} \ne \text{编程语言} $$

- CUDA 程序**用某种语言书写（最常是 C++）**，然后**由 nvcc 之类编译器编成 CPU 和 GPU 两部分代码**
- **"kernel" 就是一段做并行计算的函数**——**看到"CUDA kernel"可以把它替换成"一段为 NVIDIA GPU 写的代码"**

### 1.2 一个对照：同样是数组翻倍

**CPU 上**：线性时间，**逐个元素顺序翻倍**。
**GPU 上**：**几千个元素同时处理**。

**作者由此提出本章最重要的一个认知转变**：

$$ \boxed{\text{写 CUDA kernel 把推理工程从"思考算法"转变成"思考实现"}} $$

**最有说服力的例证**（这个对比请记住）：

| | 代码量 |
|---|---|
| 传统 attention **算法** | 几十行 |
| **FlashAttention（同一个数学操作）** | **几万行** |

**为什么**：为了**在特定 GPU 上以更省内存的方式实现同一算法**。

> 💡 **这和你 T41 的"双路径写算子"完全对应**：
> - **宏 + 脚本翻译 asm** = 全控制的"手工实现"路径
> - **intrinsics** = 编译器辅助的路径
>
> 而 FlashAttention 属于前者——**为特定硬件手写的、牺牲通用性换效率的实现**。这个类比可以在面试里帮你说清"算法相同、实现不同"的价值。

### 1.3 不要从零造：BLAS 谱系

**prior art 比 CUDA 早几十年**：

| 层 | 内容 |
|---|---|
| **BLAS** | Basic Linear Algebra Subprograms，**1970 年代为 Fortran 首次实现**，是点积到矩阵乘的通用规范 |
| **cuBLAS** | BLAS 的 CUDA 实现，**提供必需线性代数操作的预构建 kernel** |
| **cuDNN** | CUDA Deep Neural Network，**神经网络原语** |
| **GEMM** | **General Matrix-Matrix Multiplication——推理里最常用的操作** |

**为什么 GEMM 最重要**：**模型里每个线性层都用矩阵乘法**，而 cuBLAS 提供了很强的起点。

**但你不受限于 cuBLAS**：因为 GEMM 如此关键，**你可能需要更细粒度的控制**——比如**为不同形状的矩阵写不同的 GEMM kernel**，或为了在特定架构上跑得更好。

**更高层的模板库**：

| 库 | 用途 |
|---|---|
| **CUTLASS** | C++ 模板库，**写高性能 kernel 的积木**（**FlashAttention 3 就用了它**）|
| **CuTe** | 另一套模板库，**为分块（tiled）张量操作引入抽象**，面向较新架构 |
| **FlashInfer** | **LLM 推理 kernel 的高性能实现库**，含许多优化 attention kernel 和融合采样函数 |

### 1.4 Kernel 选择 ⭐ —— 多数推理工程师的实际工作

**作者的重要判断**：

> **"大多数推理工程师永远不需要自己写 kernel。但是 kernel 选择——从一系列选项里挑最好的那个——是推理优化的重要部分。"**

**为什么实现和硬件绑得这么死**（这段是面试好素材）：

- kernel 里**常有硬编码的值**，基于特定 GPU 的**内存带宽、Tensor Core 数量或布局**
- **为 H100 写的 kernel 大概率无法利用 B200 的架构和额外内存**
- **为 B200 写的 kernel 可能与上一代 Hopper 不向后兼容**
- **"每代 GPU，把手写 kernel 移植到新架构上都需大量工程工作"**

**选择的三种层次**：

| 层次 | 说明 |
|---|---|
| **自动（多数情况）** | 框架和引擎有预配置 kernel；**PyTorch 和 TensorRT-LLM 在编译步骤里做自动 kernel 选择** |
| **手动（少数关键算法）** | 为关键算法手动挑几个 kernel 来加速 |
| **自己写** | 极少数人 |

**一个精彩的具体例子**：

> 多数生产级 GEMM kernel 来自 cuBLAS。但 **DeepSeek 发布 DeepSeek-V3 更新版时，同步放出了 DeepGEMM**——**在 Hopper 架构上做 FP8 矩阵乘的更高效 kernel**。

**手动选择 kernel 让你能把 DeepGEMM 当插件插进去加速某一步**（比如乘两个特定尺寸的矩阵）。
**但作者立刻警告兼容性代价**：

> 如果你升级到 B200，就得**要么把 kernel 换回来、要么等 DeepGEMM 支持 Blackwell、要么自己移植**。

> 💡 **"插件化 kernel + 硬件换代就失效"这个模式，和 T41 的代际迁移是同一件事**。你手工优化的 asm/intrinsics 代码，换个 NPU 型号就要重做——**这正是"AI 编译器"这类工作的存在理由**（把手工移植变成可重定向的编译流程）。

### 1.5 Kernel 融合 ⭐⭐ —— 用一个极简例子讲透

**问题**：**两个不同 kernel 背靠背跑同一份数据，会产生浪费的读和写。**

**作者的极简例子**：假设两个 kernel，`multiply_by_2` 和 `multiply_by_3`：

```
不融合（6 步）：
  1. 从内存读入 [1, 2, 3]
  2. 跑 multiply_by_2
  3. 把输出 [2, 4, 6] 存回内存     ←┐
  4. 从内存读入 [2, 4, 6]          ←┘ 这两步是无意义的内存往返
  5. 跑 multiply_by_3
  6. 保存最终输出 [6, 12, 18]

融合后（3 步）：乘数合并成 multiply_by_6
  1. 从内存读入 [1, 2, 3]
  2. 跑 multiply_by_6
  3. 保存最终输出 [6, 12, 18]
```

**为什么这在推理里代价高昂**：

> **"在 decode——LLM 推理的带宽受限阶段，推理引擎付不起多余的内存读写。"**

**实践中融合比这复杂得多**，但有**常见模式**：

$$ \text{矩阵乘} + \text{加 bias} + \text{激活} \quad\Longrightarrow\quad \text{一个融合 kernel} $$

**自动 vs 手工**：

| 方式 | 谁做 | 例子 |
|---|---|---|
| **自动** | 编译器能识别**直白的**融合机会 | torch.compile 的自动融合 |
| **手工** | **更复杂的算法需要手写融合 kernel**，通过插件在推理时使用 | **FlashAttention** |

> 💡💡 **这是整章和你 T41 经验最贴合的一节**：
> 
> **kernel 融合 = 减少中间结果的内存往返**。
> 
> - 你在 T41 做的**"循环内 if 消除 + 索引复用"**，目的就是**少搬数据、多复用同一份片上数据**
> - **pingpong 双缓冲**是让搬运被计算掩盖
> - **切 NNMAC 能吃的块**是提高算术强度（[03](03_模型机制与瓶颈计算.md) 的 $I$）
> 
> **而 kernel 融合是从另一个角度做同一件事**：把"算完存、存完读"的两段合成一段，**直接从源头消灭 $N^2$ 那部分流量**。
>
> 用 roofline 语言说：**融合提高 $I$**（流量减少了，运算量不变）。这也是为什么 [03](03_模型机制与瓶颈计算.md) 里 FlashAttention 能把 attention 从"永远带宽受限"翻到"算力受限"。

## 2. 深度学习框架与库

### 2.1 PyTorch 是明确赢家

作者对其他两个只简略提了一句：

| 框架 | 现状 |
|---|---|
| **PyTorch** | **明确的领导者**（原 Meta，现属 Linux Foundation），训练与推理的行业标准 |
| TensorFlow | **2010 年代 ML 时代很显眼，今天已失宠** |
| JAX | **和 Google 非官方相关的研究项目**，界面更简单但"**正如文档所警告的，要预期有 sharp edges**" |

**作者的个人证言很有说服力**（说明 PyTorch 的定位）：

> "我个人整个职业生涯都是 Python 程序员，**我觉得写底层 C++ 很难**。用 PyTorch 我可以用 Python 写高性能推理代码，跑在 CPU 和 GPU 上，**但我随时可以下探到 CUDA 去插具体 kernel**。"

**PyTorch 的两个关键能力**：

| 能力 | 说明 |
|---|---|
| **autograd** | 对任何可微函数**自动算梯度**——这是它训练强大的原因（定义计算图，就得到梯度） |
| **torch.compile** | 把模型从训练态转到推理态；**针对特定 GPU 做自动 kernel 选择和融合** |

**torch.compile 的一个重要局限**（容易踩）：

> **"torch.compile 无法融合 plugin kernel，比如 DeepGEMM、FlashAttention 或自定义 kernel。这限制了它在 LLM 推理中的用处——LLM 里大多数 kernel 都是自定义的。"**

**那它什么时候有用**：**优化不常见的模型架构**，或者编译**长串的轻量 kernel**。
**一个实操坑**：优化自定义/罕见架构时，**可能要把函数重写得更抽象**（尤其是避开 Python 特有的语言特性）**才能让编译成功**。

### 2.2 模型文件格式

**主流格式是 `safetensors`**（Hugging Face 出的）。

**"safe" 体现在哪**（这个理由很重要）：

> **通用格式（如 `bin`）在反序列化时可以执行任意 Python 代码；而 safetensors 只存张量数据，不存可执行代码。**

**另一个关键特性**：**用内存映射**，所以**文件可不分配全量内存就加载**——让权重加载**更快更安全**。

**生成式模型有几百 GB 权重**，**分散在几十个 safetensors 文件里**。

**ONNX 的区别（重点）**：

| 格式 | 存什么 |
|---|---|
| **safetensors** | **只存权重**（参数与架构分离） |
| **ONNX** | **权重 + 模型的计算/执行图**（打包在一起） |

**ONNX 的优势**：**高度可移植**，**与 PyTorch 深度集成、支持多种硬件**——**当你需要存模型图而不只是权重时，ONNX 是 safetensors 的绝佳替代**。

### 2.3 ONNX Runtime vs TensorRT ⭐

| | **ONNX Runtime** | **TensorRT** |
|---|---|---|
| 性质 | **开源，与 Linux Foundation 相关** | **专有与开源混合，NVIDIA 造的** |
| 生态 | **PyTorch 生态里的一等导出器** | 通过 **Torch-TensorRT** 与 PyTorch 集成 |
| 硬件 | **支持多种 GPU** | **仅 NVIDIA GPU** |

**导出流程有点像 Torch 编译**，但**有个重要限制**：

> **这些标准并不支持 PyTorch 里的每个数据结构、类型和操作。导出过程能识别这些问题，但模型越复杂越棘手。**

**一个具体例子**：**DeepSeek V3 引入了 Multi-Latent Attention（MLA）**——**PyTorch 里实现的 MLA 很难导出**，但**transformer 架构整体足够简单，手写融合 kernel 是可行的**。

**⚠️ 一个重要的行业判断（这段请精读）**：

> **"今天越来越流行从 PyTorch 直接跳到 vLLM 或 TensorRT-LLM 这类推理引擎（对这些引擎支持的模型而言），绕过中间表示这一步，权重只以 safetensors 导出。ONNX Runtime 和 TensorRT 仍被广泛使用（TensorRT 尤其因为它对图像和视频模型有很强的开箱运行时），但行业正在'手写 PyTorch 代码的控制力'与'预构建推理引擎的便利'之间分化。"**

**归纳成一条趋势**：

```
旧路线：PyTorch → ONNX / TensorRT 中间表示 → 部署
新路线：PyTorch → 推理引擎直连（权重只存 safetensors）   ← 正在流行
```

> 💡💡 **这一节直接对应你的 Lesson 01-12（ONNX Runtime 自定义算子）**：
> 
> 你花 12 课学的那条路——**写自定义算子、打包成 .so 给 Python 加载、形状推断、IoBinding 零拷贝**——正是**"中间表示路线"**的核心技能。
> 
> **这条路线正在被"引擎直连"分流，但并没有死**，原因是：
> 1. **TensorRT 在图像/视频模型上仍因开箱性能强而被广泛使用**
> 2. **ONNX 作为可移植的图格式，在跨硬件（非 NVIDIA）场景里仍是主力**
> 3. **自定义算子能力是"引擎覆盖不到的地方"的兜底**——引擎支持不了的架构，还得落回到这条路
> 
> **面试价值**：如果你能说清"为什么有了 vLLM 还需要 ONNX Runtime"，就展现了你对生态演进的判断力，而不只是会用工具。**你的答案应该是：引擎给的是"常见架构的便利"，ORT 给的是"任意图的控制力 + 跨硬件可移植性"，两者是约束与通用性的权衡（对应 [01](01_全景_三层与六技术.md) 的"约束越多性能越好"）。**

### 2.4 transformers / diffusers 的真实定位

**作者说得很直白**：

> **这两个库虽然建立在 PyTorch 之上，但不是为大规模生产推理设计的。它们提供的是参考实现，供推理工程师学习和改造。**

| 用途 | 适合 |
|---|---|
| **学习/理解模型的确切输入输出规格** | ✅ |
| **在 notebook 里跑本地推理** | ✅ |
| **生产环境** | ❌ ——应该**直接写并编译 PyTorch 代码，或用生产级推理引擎** |

**但仍有两个不可替代的价值**：
1. **模型卡里的 config.json**（含必要信息）
2. **Hugging Face 相关操作的实用工具**（如下载权重）——**被广泛使用**

> 💡 这条对你有实际意义：**模型卡里的 transformers 样例代码是读"输入输出 spec"的最佳来源**，但别把它当部署方案。你在做 ONNX 转换时，样例代码正是你核对输入形状/预处理的参照。

## 3. 三大推理引擎

### 3.1 总览对比

| | **vLLM** | **SGLang** | **TensorRT-LLM** |
|---|---|---|---|
| **性能** | 好 | 好 | **最好** |
| **易用** | 易 | 易 | **难** |
| **模型支持** | **最多** | **最多** | 部分 |
| **硬件** | **GPU、TPU** | **NVIDIA、AMD** | **仅 NVIDIA** |
| **许可** | Apache 2.0 | Apache 2.0 | Apache 2.0 |

**共同点**：**三个都开箱支持核心特性**（**continuous batching / in-flight batching**），**都支持主要的性能优化技术**——训练后量化、投机解码、前缀缓存、并行、拆解。

**引擎的价值在于"可配置"**：

> **"用预先优化好的组件工作，意味着你的时间花在测试组合上，而不是重复地、糟糕地重新实现同一个 attention kernel。"**

**图像/视频生成的支持情况**：
- 2025 年底 **vLLM 和 SGLang 开始支持**（通过 **vLLM Omni** 和 **SGLang Diffusion**）
- **TensorRT-LLM 不支持图像或视频生成模型**

### 3.2 vLLM

| 项 | 内容 |
|---|---|
| 份额 | **最大**（GitHub star **是另两个之和的两倍**） |
| 起源 | **2023 年夏，UC Berkeley**；现属 **PyTorch Project（Linux Foundation 下）** |
| 最强卖点 | **广度**——NVIDIA/AMD/Intel GPU + **Google TPU**，**几乎所有开放模型的 day-zero 支持** |
| 多模态 | **vLLM Omni** 扩展到图像、音频、视频的输入输出 |

**作者对其定位的诚实评价**（这段很值）：

> **"推理工程的核心原则之一是——你能引入的约束越多，能达到的性能越好。vLLM 的宽平台在配置得当时能取得令人印象深刻的成绩，但按我的经验，它达不到 TensorRT-LLM 这类窄框架能达到的上限。"**

**什么时候用 vLLM**：
- 想**快速搭起**一个对几乎所有开放模型都有**扎实开箱性能**的服务
- 想跑**多输入多输出的 Omni 模型**
- 用的是**较小的 GPU 或较老的架构**，TensorRT-LLM 在那里没什么性能优势

### 3.3 SGLang

| 项 | 内容 |
|---|---|
| 起源 | **2023 年 12 月**，LMSYS Org |
| 崛起路径 | **与中国开放模型（DeepSeek、Qwen）一同崛起**；**是 xAI 的引擎选择** |
| **差异化** | **把快后端运行时和灵活的前端语言配对**——**你可以为深度定制挑单个组件，而不必重写其他部分** |
| 协作 | 与 **DeepSeek、Qwen、Kimi、Z AI** 密切合作，**第一时间出优化实现**（如 DeepSeek 的 MLA） |
| **重注方向** | **大规模 MoE LLM 部署**——**特别是 GB200 NVL72 这类系统上的多节点部署，追求高吞吐** |
| 图像视频 | **SGLang Diffusion** |

**SGLang Diffusion 的设计值得记一句**：引入**流水线抽象来编排多个 stage**，**这种灵活方式与图像/视频生成模型的架构高度契合**；性能上加了**各种扩散专用并行方法**，并**复用主 SGLang 包的调度器和优化 kernel**。

**什么时候用 SGLang**：
- 想在**大 MoE 模型（DeepSeek、Kimi）**上拿到**优秀的开箱吞吐**
- 想要**图像/视频生成模型的引擎体验**
- 想要**控制力和定制**，并且**乐于参与 SGLang 社区**

### 3.4 TensorRT-LLM 与一个必须知道的命名坑 ⚠️

**有重大版本差异，且生产里两个大版本都常见**：

| 版本 | 性质 |
|---|---|
| **V0（0.X.Y）** | **是 NVIDIA TensorRT 的插件** |
| **V1（1.X.Y）** | **基于 PyTorch 的独立包，不依赖 TensorRT** |

**为什么性能最好**：**能用 NVIDIA 工程师写的 kernel，其中有些是闭源的**。这些手写、手工融合的 kernel **对最新架构（Hopper、Blackwell）和 NVIDIA 专有格式（NVFP4）支持极好**。

**另一个亮点**：**in-flight batching（token 级连续批处理）实现很健壮**，有助于吞吐。

**支持的优化几乎全套**：量化、投机算法、前缀缓存、**chunked prefill**、灵活并行、拆解。

**代价（作者列得很全）**：
- 学习曲线陡
- **模型支持更窄，新架构到得更晚**
- **仅 NVIDIA**
- **不做图像或视频生成**

**开发体验**：V1 之后看起来很像 vLLM/SGLang，但**除 `trtllm-serve` 的命令行参数外，还期待一个 `config.yaml` 做更深定制**。
**安装建议**：**最好通过 NVIDIA 官方 Docker 容器运行。**

**什么时候用 TensorRT-LLM**：
- 跑的是**支持良好的架构**，且在 **Hopper 或更新的 GPU** 上
- **愿意做额外工程工作**换取尽可能好的性能
- （可选）打算用 **NVIDIA Dynamo**，想要集成最深的引擎

> 💡 **作者自述 Baseten 三个都用，但 TensorRT-LLM 用得最多**——这本身就是"高性能场景往窄框架走"的证据。

## 4. NVIDIA Dynamo：引擎之上的编排层

**定位**：**2025 年 3 月 GTC 发布**的分布式模型服务系统。**三种引擎都能当后端**，Dynamo 自己**提供大规模部署的编排层**。

**提供三件核心能力**：

| 能力 | 说明 |
|---|---|
| **KV cache 复用** | 在请求间保留 KV 信息，**并按前缀匹配路由请求** |
| **Disaggregation** | **把 prefill 和 decode 拆到独立优化、独立扩缩的引擎上** |
| **多节点并行** | （可选）单个模型副本用两个以上节点，**通常配专家并行** |

**最有意思的功能**：**基于 SLA 的 planner**——**你可以自动扩缩 prefill 和 decode worker，约束是你自己定义的 TTFT 和 TPS 目标。**

**作者的重要判断（避免过度使用）**：

> **"Dynamo 是为规模造的：大模型、大流量。"** 它服务于把万亿参数级模型（如 Kimi 家族）**推给大量并发用户**。
>
> **"但很多部署不需要 Dynamo 的额外复杂度。除非你的量级已经大到 disaggregation 和 KV-aware 路由真正起作用，否则 Dynamo 就是多余的工作和开销。这些情况下你直接用推理引擎就行。"**

> 💡 **这段又一次体现 [01](01_全景_三层与六技术.md) 的原则二**：**"流量越大，能做的优化越多"**。没到量级就别上复杂度——**这是个能帮你避免过度设计的判断**。

## 5. 基准测试与性能分析

### 5.1 最高标准：影子流量

> **"最好的基准是把真实生产流量影子复制到你要测试的系统上。"**

**shadowing** = 把进来的请求复制一份到测试系统，**这样可以在不影响原请求的前提下测它的性能**。

### 5.2 模拟流量要匹配的四个维度（很实用）

| 维度 | 为什么 |
|---|---|
| **序列长度**（ISL/OSL） | **TTFT 和内存用量依赖输入/输出序列长度** |
| **流量规模与模式** | batching 和服务器负载依赖并发请求数；**要加抖动（jitter）模拟真实使用** |
| **请求内容** | **实际 prompt 影响缓存命中率和草稿 token 接受率** |
| **输入参数** | temperature、reasoning effort 这类**要设成预期的生产值** |

**作者的点睛之笔**：

> **"记住，优化是关于权衡和约束的。如果你在拿糟糕的输入去最大化基准性能，生产中的表现就不会符合预期。"**

### 5.3 工具

| 工具 | 说明 |
|---|---|
| **SGLang Genai-bench** | CLI + 仪表板，**对任何框架部署的模型**都能压测 |
| **NVIDIA GenAI-Perf** | 客户端工具，测多样流量下的延迟与吞吐 |
| **Locust** | 通用开源压测工具，**非生成式 AI 专用**，可模拟最多百万级并发用户 |

**还有一个巧思**：**用开源的 evals 数据集当压测输入**（MMLU、gsm8k、SWE-bench 等）。它们有两个用途：
1. 提供**有变化的、真实的输入**
2. **顺便抽查性能优化有没有影响输出质量**

**选数据集要贴合生产用途**：比如**给代码补全系统降延迟就用 HumanEval**。

### 5.4 基准测试技巧（四条）

1. **先建立扎实的基线**（做任何优化之前）
2. **保持一致配置**；**单个测每个优化，也测组合**，才能完全理解是什么在驱动改进
3. **有些优化会互相打架**——**比如大 batch size 下跑投机解码**
4. **一次只改一个变量**——"这条原则也适用于你的基准配置"

### 5.5 Profiling：比 benchmark 深一层

**作者对区别的定义非常清楚**：

| | 回答什么 | 例子 |
|---|---|---|
| **Benchmark** | **你的系统表现如何** | "P90 TTFT 是 350ms" |
| **Profiling** | **为什么会这样表现** | 那 350ms 分别花在哪 |

**一个重要的"谁需要它"的判断**：

> **大多数推理工程师不需要把 profiling 作为日常工作**。用 TensorRT-LLM 这类已经高性能的工具时，**你的工作流是"配置—基准测试"的循环，profiling 是多余的**。
>
> **但如果你是**：给 vLLM/SGLang 这类框架做贡献、**自己用 PyTorch 写推理服务**、或在**视频生成这类新模态的最前沿**工作——**profiling 应该成为你工具箱的一部分**。

**工具三件套**：

| 工具 | 特点 |
|---|---|
| **PyTorch Profiler** | 易用，抓逐步性能指标（CPU 时间、GPU 时间、内存用量） |
| **NVIDIA Nsight Systems（NSys）** | 功能丰富但复杂，**GPU/CPU 采样与追踪，跨多 GPU 及其互联做系统级分析** |
| **NVIDIA Nsight Compute（NCU）** | **深入分析单个 CUDA kernel** 的算力和内存用量（**对单个 kernel 问 [roofline](03_模型机制与瓶颈计算.md) 问题**）|

**一个完整的工作流例子**（说明 profiling 怎么指导优化）：

> 用 PyTorch Profiler 发现**激活函数耗时异常长，原因是多余的内存读取** → 想办法**写一个融合 kernel，让激活和 attention 一起跑**以消除那些读取 → **把新 kernel 插进 PyTorch 代码** → **重跑系统级基准**，看是否达到延迟目标。

> 💡 这个例子把本章两条主线串起来了：**profiling 发现问题（多余内存读取）→ kernel fusion 解决问题**。而"多余内存读取"正是 [03](03_模型机制与瓶颈计算.md) 说的"$I$ 太低、撞带宽墙"。

## 6. 本章小结与自测

### 关键认知

1. **硬件迭代慢、软件迭代快**——这是推理工程版图广阔的原因
2. **CUDA 不是语言**，是用 C++ 写、nvcc 编译成 CPU/GPU 两部分
3. **写 kernel = 从"思考算法"转向"思考实现"**：attention 几十行，FlashAttention 几万行
4. **BLAS（1970s Fortran）→ cuBLAS → GEMM 是推理最常用的操作**；CUTLASS/CuTe/FlashInfer 提供更高层积木
5. **多数人不需要写 kernel，但需要做 kernel 选择**；**kernel 与硬件强绑定，每代 GPU 都要大量移植工作**
6. **kernel 融合 = 消灭中间结果的内存往返**；decode 阶段（带宽受限）付不起这个代价；常见模式是"矩阵乘+bias+激活"
7. **PyTorch 是明确赢家**；**torch.compile 无法融合 plugin kernel**（DeepGEMM/FlashAttention/自定义），限制其在 LLM 的用处
8. **safetensors 只存张量（不存可执行代码）+ 内存映射**；**ONNX 存权重 + 计算图**
9. **行业趋势：PyTorch → 引擎直连，绕过中间表示**；但 TensorRT 在图像视频仍强、ONNX 在跨硬件仍主力
10. **transformers/diffusers 是参考实现，不是生产方案**（但 config.json 和样例代码很有用）
11. **三大引擎的取舍：vLLM 广、SGLang 强在 MoE 与可定制、TensorRT-LLM 最快但最窄**
12. **TensorRT-LLM 的命名坑：V0 是 TensorRT 插件，V1 是独立 PyTorch 包**
13. **Dynamo 是为规模造的**——没到量级就是多余复杂度
14. **benchmark 说"表现如何"，profiling 说"为什么"**；用引擎的人主要做"配置—基准"循环
