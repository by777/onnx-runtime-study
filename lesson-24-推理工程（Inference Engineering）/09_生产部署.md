# 09 生产部署

> **对应原书**：Chapter 7: Production
> **本课定位**：模型之外的基础设施——容器、扩缩、多云、可观测。
> ⚪ **按你的方向，这一章建议泛读**：它服务云上运维和采购决策，和芯片工具链关系不大。但**其中几条判断（冷启动、批量策略、独立扩缩）在其他场景也有迁移价值**，我会标出来。

## 0. 这一章要解决的问题

**核心矛盾**（作者立论）：

> **"无论单个实例服务一个模型能有多快多高效，流量足够大时服务都会被压垮。这不是 PyTorch 问题也不是 CUDA 问题，是基础设施问题，需要不同的思维方式和不同的技术。"**

**三个新复杂度**：

1. **在哪、怎么拿到 GPU**
2. **怎么在它们之间平衡流量**
3. **怎么防止停机**

**外加一个容易被忽略的点**：

> **"延迟不只来自 prefill 和 decode。你需要端到端评估系统，消除 server、网络、甚至客户端（在你能影响客户端代码的情况下）的低效。"**

> 💡 **这一条呼应 [02](02_前置决策_度量与模型选择.md) 的诊断规则**：**"推理快但端到端慢 → 去查基础设施"**。这一章就是那一步的具体工具箱。

## 1. 容器化

### 1.1 基础概念

**容器为什么轻量**：

$$ \text{容器共享底层宿主 OS 内核（指 Linux 内核，不是 CUDA kernel）} $$

**术语**：

| 术语 | 含义 |
|---|---|
| **Container** | 正在运行的、隔离应用与其依赖的环境 |
| **Image** | 可执行包，包含运行软件所需的一切 |
| **Dockerfile** | 人能读、机器能解释的指令文件，用于创建镜像 |
| **Registry** | 镜像的中央仓库 |

**一个有用的类比**：

$$ \text{Docker Hub 之于镜像} \;\approx\; \text{Hugging Face 之于模型权重} \;\approx\; \text{PyPI 之于 Python 包} $$

**三层结构**：

| 层 | 内容 |
|---|---|
| **Base image** | OS 发行版（如 Ubuntu）或从 registry 取的更复杂镜像 |
| **附加层** | Dockerfile 指令指定的文件系统变更（依赖、代码、配置） |
| **Container layer** | **运行时创建的薄而短暂的一层**——**运行中的改动写在这里，容器终止就丢失** |

**实用建议**：**推理引擎（vLLM、SGLang）会为活跃版本提供官方基础镜像，通常应该从这些验证过的镜像开始，而不是从零构建。**

### 1.2 依赖管理：为什么容器化是必需的

**问题描述**（很准确）：

> **"推理的依赖链又长又脆。能构建出一个能跑的版本很难，这让容器化变得必需——因为在一个破坏性变更如此常见的生态里，你需要保住那个已知可用的构建。"**

**镜像里包含什么**：

| 组件 | 说明 |
|---|---|
| **CUDA toolkit 版本** | CUDA、cuDNN、驱动的具体版本 |
| **Python 包** | torch、transformers、diffusers 等 |
| **推理引擎** | vLLM/SGLang/TensorRT-LLM 的版本 |
| **系统包** | 如 ffmpeg（**处理音频、图像、视频模型时特别常见**）|

**两条最佳实践**：

**① 打包要轻**

> 为推理构建的镜像常达几 GB。"**像背包徒步者一样，你要轻装。**"

**② 版本要钉死（pinning）**

> **"钉死的依赖树让系统运行行为在不同环境间保持一致，并让镜像可重复构建得到相同结果。"**

**一个很真实的场景**：

> **"新模型发布时，整个推理生态抢 day-zero 支持。为新模型构建镜像时，推理工程师常依赖夜间构建或其他开发者预发布版依赖，而不是稳定版。这些早期版本更容易有 bug，常常需要在模型发布后几天到几周内重建到稳定版。"**

> 💡 **这一段对你有直接价值**。你做端侧部署时应该已经体会过"依赖地狱"：**QNN SDK 版本、ONNX 版本、NDK 版本三者的兼容矩阵**。**作者的建议（钉死版本 + 从验证过的 base 开始 + 保存可重复构建）可以直接用在你的板端部署流程里**——你的 `build/`、`tvm-bin-arm/`、`mnn-src/` 这些目录其实就是"已知可用构建"的物理体现，**显式记录版本矩阵会让它更可靠**。

### 1.3 NIMs（NVIDIA Inference Microservices）

**定义**：**为流行开放模型预构建的 Docker 容器。**

| 类型 | 说明 |
|---|---|
| **Multi-LLM NIM** | **灵活容器**，在支持的 GPU 架构上跑一个模型家族 |
| **LLM-specific NIM** | **为特定模型在特定 GPU 上配置成最大性能的引擎** |

**它能怎么用**：**当起点、当参考架构、当开箱服务。**

**⚠️ 但作者给了个明确的边界**：

> **"如果你要的是最大控制权而不是一个替你做好的配置，你通常更适合从一个更少预设的基础镜像自己构建容器，而不是改造 NIM。"**

> 💡 **这又是"约束越多性能越好"原则的应用**——**NIM 是"约束已经替你定好"，代价是灵活性。**

## 2. 自动扩缩（Autoscaling）

### 2.1 目标和两种信号

$$ \text{目标是：足够的资源服务所有进来的请求 + 维持延迟 SLA + 不为闲置 GPU 浪费钱} $$

**基于 Kubernetes**（control plane 做决策 / worker plane 跑容器）。

**两种扩缩信号**：

| 信号 | 说明 |
|---|---|
| **Utilization（利用率）** | 基于 GPU 利用率信号（内存使用、算力使用）|
| **Traffic（流量）** | 基于系统正在处理的请求数 |

**⭐ 两者不总是一致——作者举了个很精辟的例子**：

> **"在 LLM prefill 里，少数几个带几十万未缓存输入 token 的请求，会比大量高缓存命中率的小请求造成高得多的利用率。"**

**结论**：

$$ \text{流量信号可以【前瞻性】决策} \qquad \text{利用率是【滞后】指标} $$

$$ \Longrightarrow \text{两者配合使用} $$

### 2.2 流量型扩缩的五个参数（实用清单）

| 参数 | 含义 |
|---|---|
| **Min replicas** | 无论流量如何都保持运行的最小副本数 |
| **Max replicas** | 高流量时最多能分配的副本数 |
| **Autoscaling window** | 用来度量流量、做扩缩决定的**滑动时间窗** |
| **Scale down delay** | 建议缩容后**等多久**，以防又来一波流量尖峰 |
| **Concurrency target** | **每个副本能同时处理多少请求** |

**作者的权衡说明**：

> **"加大 scale down delay 能防止对尖峰流量过早缩容，但可能在流量真正冷却后造成不必要的开支。"**

### 2.3 批处理的三种方式 ⭐（这张对比很有用）

| 方式 | 行为 | 问题 |
|---|---|---|
| **Static batching** | 服务器**等 batch 满了才开始**推理 | **早期请求等待时间长** |
| **Dynamic batching** | 等到 batch 满**或**配置的时间过去了才开始 | 折中 |
| **Continuous batching** | **服务器持续推理，有空位就把请求换进来** | 三大引擎都实现，**相对 static 显著降低延迟** |

**作者补充**：**vLLM、SGLang、TensorRT-LLM 实现的是健壮的连续批处理**（TensorRT-LLM 叫 **in-flight batching**），**在 token 级别做批处理**。

**batch size 的取舍（核心旋钮）**：

| 加大 batch size | 后果 |
|---|---|
| 总吞吐 | **提升** |
| 每个用户的延迟 | **变差** |

$$ \text{要跨多个 batch size 测性能，为你的模型、实例、延迟目标、预算找到合适的点} $$

**配置的一致性要求**：

$$ \text{autoscaling 层的 concurrency target} \;\longleftrightarrow\; \text{副本层的 batch size} \quad \text{（两者应该匹配）} $$

**⭐ 扩缩的判据（很清晰，可直接用）**：

| 观察 | 动作 |
|---|---|
| **所有活跃副本都到达最大并发** | **扩容** |
| **足够多副本在跑半满的 batch** | **缩容** |

> 💡 **这段（batch 策略 + 扩缩判据）是本章最可迁移的部分**。它的本质是**用"延迟-吞吐曲线"而不是"单点性能"来做容量决策**——**这个思维方式和你做板端部署时的"留多少余量"是同一类问题**：
> - 板端：RTF 0.044 意味着延迟余量充裕，**那余量应该用来提高并发/加功能，还是留着抗抖动？**
> - 云上：**batch size 和 concurrency target 就是同一个旋钮**
>
> **能看出这两者的同构，说明你理解了"延迟-吞吐是一个曲线而不是一个数字"。**

### 2.4 冷启动 ⭐（这一节有很强的通用价值）

**定义**：**把一个模型副本从零启动起来所需的时间。**

**为什么它决定扩缩质量**：

> **"自动扩缩系统的整体表现取决于它的冷启动速度。如果你不能快速启动副本，就很难有信心缩容，从而过度配置。"**

$$ \text{冷启动慢} \;\Longrightarrow\; \text{不敢缩} \;\Longrightarrow\; \text{过度配置} \;\Longrightarrow\; \text{浪费钱} $$

**四个影响因素（每个都要单独优化）**：

| 因素 | 说明 | 谁能优化 |
|---|---|---|
| **GPU procurement** | 多快能把 GPU 加到集群并分配给模型？ | **主要取决于云供应商**（除非有热节点池）|
| **Image loading** | 多快能把容器镜像加载到新实例？ | **工程师** |
| **Model loading** | 多快能把权重加载进容器？ | **工程师** |
| **Engine startup** | 多快能启动推理引擎（**含编译时间**）？ | **工程师** |

**工程师能做的三件事**：

**① 让镜像和权重更小**

$$ \text{加载镜像和权重} = \text{"能多快写入几 GB 到几百 GB 数据"} $$

$$ \Longrightarrow \text{只有两条路：让它更小，或带宽更高} $$

> **"只包含必要步骤和依赖能让镜像更小、构建更快；而【量化模型权重】有一个额外好处——冷启动时加载更快。"**

**② 关于"把权重烤进镜像"的历史变化**（这个观察很有意思）

> **"对小模型，过去的策略是把权重烤进镜像以简化缓存和加载。但现在大多数模型有几十上百亿参数，权重比镜像大得多，单独加载更好。"**

**③ 权重从哪加载对带宽影响巨大**

| 来源 | 问题 |
|---|---|
| 第三方（如 Hugging Face） | **受其出网速度限制** |
| S3 桶 | 引入网络延迟 + 数据传输费 |

**最佳做法**：

> **"加载几百亿参数模型需要每秒 GB 级的带宽。得到这个的最好方式是在【同一数据中心内】、从【物理上靠近 GPU 实例】的源、【经网络在节点内】加载。"**

**④ 编译时间与引擎缓存**

| 引擎 | 启动 |
|---|---|
| vLLM、SGLang | **启动快** |
| **TensorRT-LLM、带优化的 PyTorch** | **有编译步骤，针对特定硬件构建引擎，常要几分钟** |

**⚠️ 缓存引擎能极大改善冷启动，但有个硬约束**：

> **"你总是需要把缓存的引擎加载到一个 GPU 型号、CUDA 版本、软件依赖都和构建该引擎时完全相同的实例上，它才能正确运行。"**

> 💡💡 **第四节"引擎缓存 + 环境必须完全一致"这条，和你的工作直接同构**：
>
> 你做交叉编译时，**"编译产物必须和运行环境严格匹配"**是天天要面对的事：NDK 版本、ABI、glibc 版本、QNN SDK 版本、HTP 架构版本……
>
> **本节的表述给了你一个更一般的框架**：
> $$ \text{编译期绑定} \;\Longrightarrow\; \text{产物与目标环境强耦合} \;\Longrightarrow\; \text{需要缓存 + 环境指纹校验} $$
>
> **这正是"AI 编译器"要解决的核心痛点之一**（把"为每种目标重新编译"变成"可重定向的编译流程 + 可缓存的产物"）。**面试时如果聊到工具链的价值，这是一个很好的切入点。**

### 2.5 路由、负载均衡、队列

**两个概念的区别（作者区分得很清楚）**：

| 角色 | 回答什么 |
|---|---|
| **Router（路由器）** | **"这个请求【应该】去哪？"**——请求级 |
| **Load balancer（负载均衡器）** | **"这个请求【可以】去哪？"**——系统级，均匀分散 |

**复杂系统里两者都不止一个**：**路由发生在整个栈里，负载均衡器注入在关键点以保持系统级性能稳定。**

**⭐ 为什么不能简单地平均分配（这个例子很好）**：

> **"不是简单地说『我有 3 个副本 12 个请求，那就每个放 4 个』就行。每个请求的输入 token 数可能不同。如果多数请求是 100 个输入 token，一个 10000 token 的请求就会打破简单系统的平衡。"**

**有些请求更适合特定副本**：

| 类型 | 做法 |
|---|---|
| **KV cache-aware routing** | **把请求导向已有匹配前缀的副本** |
| **LoRA-aware routing** | **把请求导向内存里已加载所需 LoRA 权重的副本** |

**智能路由用到的信息**：**来自推理引擎和 Dynamo 这类编排器的序列长度、前缀、LoRA 需求。**

**队列**：

> **"负载均衡和路由还不够。当自动扩缩系统收到的流量超出它能处理的量，它需要一个办法暂存请求，直到扩缩出更多资源或现有资源可用。"**
>
> **队列是处理这种情况的基础设施原语。**标准队列是 FIFO，**但你可以做更复杂的实现，比如优先级队列**——例如在高流量时让付费用户优先于免费用户。

**⚠️ 一个容易出的 bug**：

> **"新副本上线后，要确保队列能看到它们，请求不要继续干等已有副本。每个新副本一旦激活，就应立即被分配最多到其并发上限的排队流量。"**

### 2.6 Scale to Zero

**定义**：无流量时缩到零个活跃副本，收到流量时自动扩起来。

**两个前提**：

| 前提 | 为什么 |
|---|---|
| **快速的冷启动** | **用户可能在等着** |
| **健壮的队列** | 需要能暂存进来的请求直到副本就绪 |

**⚠️ 但不适用于所有负载**（作者的判断很实用）：

| 场景 | 适合吗 |
|---|---|
| **开发环境** | ✅ 测试是突发性的，首次请求的延迟不重要 |
| **周期性流量的应用** | ✅ 比如只在一个国家营业时间内被访问的 agent、每天跑批处理的离线系统 |
| **延迟敏感的轻量无规律流量** | ❌ **"这通常说明你的 AI 应用还不适合专用基础设施，应该继续用按 token 付费的 API 直到量级更大"** |

### 2.7 独立组件扩缩

**背景**：**AI 应用越来越多是基于多模型、多阶段的复合 AI 负载**。

**为什么必须分开扩缩（作者的例子）**：

| 步骤 | 硬件需求 |
|---|---|
| **VAD 模型** | **远比它为之切块的转写模型弱的 GPU** |
| **转写模型** | 中等 |
| **处理转写的 LLM** | **可能要 8 卡整节点** |

> **"对这些流水线，你需要拆解扩缩决策，逐步扩缩，给每步配对的资源，避免既出瓶颈又过度配置。"**

**⚠️ 但有一个硬约束**：

$$ \boxed{\text{流水线里每个模型都应该跑在【同一个集群】里}} $$

**作者的算术很有说服力**：

> **"如果集群内发消息要 10 毫秒、跨集群要 50 毫秒，那 40 毫秒的差异在一个 5 步流水线上就是 200 毫秒，占 1 秒延迟 SLA 的 20%。"**

## 3. 多云容量管理

### 3.1 为什么"一堆孤立算力池"不算多云

> **"把多云推理做成一堆跨不同云供应商的孤立算力，是很直接的。但在这种设置里，没法流动地使用跨云算力，跨云搬负载是繁琐易错的过程。"**

**真正的多云需要**：

$$ \text{多区域、多供应商的【装箱（bin packing）】工具，把不同算力池当作可互相替代的} $$

> **"和 Kubernetes 在单个集群内一样，多云容量管理必须采取全局视角，实现自愈与全局调度。"**

**四个收益**：

| 收益 | 说明 |
|---|---|
| **Capacity** | 汇集多供应商的容量，拿到更大更灵活的 GPU 访问权 |
| **Redundancy** | 把推理分散到多供应商，抗故障 |
| **Latency** | **跑在离终端用户近的地方以减少网络延迟** |
| **Compliance** | **按数据主权和其他监管要求跑推理** |

**架构：control plane + workload planes**

| 部分 | 职责 |
|---|---|
| **Control plane** | 处理模型部署和全局扩缩决策，接收实时事件流 |
| **Workload planes** | 处理直接推理流量和集群内扩缩决策，上报利用率和需求 |

**这种职责分离的意义**：

> **"确保单个 workload plane 能独立服务流量。如果 control plane 或任何单个 workload plane 出事，其他 workload 应该不受影响。"**

### 3.2 GPU 采购

**三类供应商**：

| 类型 | 例子 |
|---|---|
| **Hyperscaler** | AWS、GCP |
| **Neocloud** | Coreweave、Nebius（GPU 专用云）|
| **Reseller** | SF Compute Company（二级市场）|

**现实约束**：

> **"很多云供应商把大部分紧俏 GPU 按长期预留分配给了最大的客户。你可能需要跨多个云供应商才能拿到合适区域的 GPU。"**

**三种采购机制**：

| 机制 | 特点 |
|---|---|
| **Reserved** | 几百到几千张卡的块，预留数月到数年，**有折扣** |
| **On-demand** | 按需单实例，**时价高** |
| **Spot** | 折扣的按需实例，**可按约定通知期被抢占（常是分钟级）** |

**⭐ 大规模推理的标准做法**：

$$ \text{低价 reserved 做基线} \;+\; \text{on-demand 和 spot 应对尖峰} \;+\; \text{分布到多个集群以贴近用户} $$

### 3.3 地理感知负载均衡

**一条很好用的经验法则**：

$$ \boxed{\text{请求穿过一个时区约需 5 毫秒}} $$

**例子**：**纽约到旧金山单程 15 毫秒。**

**推论**（呼应 [07](07_投机_缓存_并行_拆解.md) 的独立扩缩同集群约束）：

> **"考虑到延迟预算这么小，尽量让负载跑在离终端用户近的地方很重要。"**

### 3.4 为可靠性而构建

**⭐ 一组很有说服力的数据（来自 Llama 3 论文）**：

$$
\begin{aligned}
&\text{运行 } 16{,}000 \text{ 张 GPU}，\text{持续 } 54 \text{ 天} \\
&\text{经历了 } \textbf{419 次意外中断}，\text{主要是硬件故障} \\
&\Longrightarrow \text{约每 } \textbf{50{,}000 GPU 小时} \text{ 一次故障}
\end{aligned}
$$

**为什么这很吓人**：

> **"5 万小时听起来很长，但用 8 卡节点跑推理一整年就超过 70,000 GPU 小时。推理工程师应该预期硬件会故障。"**

$$ \Longrightarrow \boxed{\text{预期故障是常态，不是异常}} $$

**GPU 健康是节点级问题**：

> **"当一张 GPU 故障，同节点上其他 GPU 往往接着故障或需要下线维护。"**

**做法**：**主动记录故障、隔离节点（cordon）、轮换 pod。**

**不只 GPU 会挂**：**云供应商有计划内维护和自己的非计划停机。**

**多云的两种高可用姿态**：

| 姿态 | 说明 |
|---|---|
| **Active-active** | **多个区域/集群同时服务实时流量**；任何 plane 挂掉，流量无缝继续 |
| **Active-passive** | **热备**集群/区域就绪但空转；active 挂掉时切换过去 |

### 3.5 安全与合规

**三个关注中心**：

| 领域 | 关心什么 |
|---|---|
| **用户数据** | 所有数据（含输入输出）受保护 |
| **模型权重** | **对有微调或专有模型的公司，权重是无价的商业秘密** |
| **基础设施** | **GPU 本身和智能访问都是滥用目标** |

**⭐ 最容易的改善措施（作者的原话）**：

> **"你能做的改善安全最简单的决定之一，就是干脆【不存用户输入或模型输出】。这可能做不到——你可能有日志要求或用户协议要为了未来训练保留使用数据——但如果你不需要保留用户数据，你就能缩小攻击面。"**

**通用安全手段**：数据加密、容器安全、网络与访问控制、工作负载隔离，**并用广泛的第三方渗透测试验证**。

**多云对合规的帮助（两个具体点）**：

**① 认证传导**

> **"你的应用要符合 SOC 2 Type II 这类认证或 HIPAA 这类法规，你的供应商通常也必须合规。这种情况下，能把工作负载移到合规供应商就很有用。"**

**② 数据驻留（data residency）**

> **"某些行业和国家有数据驻留要求：来自他们国家的用户数据不能在另一个国家的服务器上处理。"**
>
> **例子**：在**多伦多附近**和**纽约附近**各有一个集群，就能**把加拿大数据留在加拿大、美国数据留在美国**，同时给区域内的用户提供最小的延迟开销。

## 4. 测试与部署

### 4.1 三种测试策略

| 策略 | 说明 |
|---|---|
| **Manual testing** | 写脚本（或点按钮）向推理服务发合成流量 |
| **Load testing** | 自动发大量流量，测系统扩缩和维持性能的能力 |
| **Shadow traffic** | **把线上流量复制到测试部署，测真实条件下的表现** |

**⚠️ 成本提醒**：

> **"测试推理服务很贵。配置测试和度量结果要工程时间，跑测试流量要 GPU。"**
>
> **省钱做法**：**影子流量测试可以先用线上流量的随机抽样开始，然后再做一次短时长的负载测试。**

**另一个易忽略点**：**AI 产品用量一般有日周期和周周期波动**，别在周期低点做结论。

### 4.2 零停机部署

**蓝绿部署（传统高可用设计）**：

| 项 | 内容 |
|---|---|
| 结构 | **两个完全相同的环境**：原 blue + 新的 green |
| 切换 | green 就绪后**全量流量一次性切过去**，blue 保持就绪以备回滚 |

**⚠️ 但它不适合大规模推理负载**（理由很实在）：

> **"如果 blue 部署用了 100 张 GPU，green 部署在流量切换前需要另外 100 张 GPU。"**
>
> **这和让大规模测试困难的 GPU 容量与成本问题是同一个。**

**⭐ 金丝雀部署（推荐）**

**名字来源**：**"受到用于检测煤矿瓦斯的金丝雀启发——金丝雀部署在错误影响大量用户之前就抓住它。"**

**四步流程**：

```
1. 构建新的推理服务部署，让它准备好处理进来的请求
2. 把【小比例】的线上流量导向新服务
3. 监控新服务，确认它正确处理流量；有任何问题就回滚
4. 逐步增加流量，同时持续监控，直到新部署承载 100% 流量
```

**优点**：

> **"金丝雀部署可以快速推出（几分钟流量爬坡），也可以慢速爬坡以确保每个阶段的稳定性。"**

**和自动扩缩的配合（很重要）**：

> **"有了自动扩缩，金丝雀部署在大规模下不会增加太多成本——因为减少给生产系统的流量会让它自动缩掉一些副本。"**

**⚠️ 但要注意一个坑**：

> **"新部署在没有流量时会默认缩到最小副本数。**在整个金丝雀过程中，要确保新部署有足够的活跃副本来正确处理请求。**否则用户会看到延迟尖峰，因为他们的请求被排队等到自动扩缩完成。"**

### 4.3 成本估算 ⭐（这节给的是思维方式）

**从按 token 付费转到自建，成本模型的根本变化**：

| 模式 | 成本函数 |
|---|---|
| **公开 API** | **简单**：每百万 token 单价 × token 数 |
| **专用部署** | **多变量函数** |

**专用部署影响成本的因素**：

| 因素 | 问题 |
|---|---|
| **Batch sizing** | 是为延迟优化（低 batch）还是为吞吐优化（高 batch）？ |
| **Traffic patterns** | 流量是否持续打满活跃 GPU，还是容量空转？ |
| **Sequence lengths** | 请求的输入/输出 token 平均是多少？异常情况下呢？ |

$$ \text{专用部署的"福与祸"都在于：成本成了多变量的函数} $$

$$ \text{好处：你有了控制权} \qquad \text{坏处：估算变难} $$

**⭐ 作者给的方法论建议（很实用）**：

> **"考虑到这种复杂度和输入/输出 token 的成本差异，【把你的 token 价格换算成总成本，然后和专用部署比较】，通常比试图从你为 GPU 付的钱反推每 token 价格更有成效。"**

**两条实操要求**：

1. **估算要用长周期**——**理想至少一周**，以平滑用量波动
2. **别忘了工程时间的成本**

$$ \text{TCO（总拥有成本）} = \text{GPU 成本} + \text{构建和维护推理系统的工程时间} $$

> **"这项投资虽然能换来更高的可靠性、安全性和控制力，但应该计入 GPU 成本以形成 TCO 的完整图景。"**

### 4.4 可观测性

**要监控什么（七个维度，清单一目了然）**：

| 指标 | 内容 |
|---|---|
| **Total volume** | 模型部署收到的请求数 |
| **Request/response sizes** | 处理中的请求的输入/输出序列长度 |
| **Response codes** | 2XX/4XX/5XX 响应码计数 |
| **Latency** | TTFT、TPS、端到端延迟，**按 P50/P90/P99** |
| **Replica count** | 活跃服务的实例数，以及正在启动的实例数 |
| **Utilization** | **CPU、host 内存、GPU、GPU 显存**的利用率 |
| **Queue depth** | 异步流量系统里已入队待处理的请求数 |

**⭐ 为什么这些指标要一起看（作者说得很对）**：

> **"这些指标是【相互依赖】的。一个延迟尖峰可能来自请求量，但也可能来自长输入序列。【一起看这些指标，让推理工程师不仅能理解发生了什么，还能理解为什么。】"**

**日志**：**服务端日志 + 显示推理服务变更的审计日志**，实时提供信息。

**⚠️ 可观测性不能孤立**：

> **"为推理构建可观测性时，要把它和现有的可观测与告警工具（Grafana、Datadog、PagerDuty、Sentry）深度集成，把推理信息放到整个应用的上下文里。"**

> 💡 **这条"不能孤立"的提醒有普遍价值**：**这是工具链思维的另一个实例**——**能提供信息的能力，必须能被用户已有的工作流消费，否则等于不存在**。

## 5. 客户端代码

**这一节容易被跳过，但它给的几个数字很有说服力。**

### 5.1 双方与常用库

| 角色 | 说明 |
|---|---|
| **Client** | 浏览器、agent、应用 |
| **Server** | 推理服务 |

**行业标准客户端是 OpenAI SDK**（支持大量兼容供应商），此外 LangChain、Vercel AI SDK、LiteLLM、LlamaIndex 等也能当客户端。

### 5.2 客户端延迟开销（⭐ 一组值得记的数字）

**建立会话**（取决于客户端网络和协议）：

$$ \text{客户端与服务器建立会话需要【几十毫秒】} $$

**⭐ 作者给的算术很有冲击力**：

> **"在一个 P95 端到端延迟 SLA 为 300 毫秒的高性能系统里，一次 TLS 握手【至少占掉延迟预算的 10%】，而这发生在推理开始之前。"**

**结论**：**同一客户端的后续请求应该通过复用已有会话省时间。**

> **"会话复用不是新想法，OpenAI SDK 这类工具在底层默默提供了它。但当你为非标准模态构建自己的客户端时，要遵循会话复用这类最佳实践。"**

### 5.3 异步推理

**适用场景**：**为吞吐而不是延迟构建的系统**——批量文档处理、语料嵌入这类对延迟不敏感的用例。

**机制**：

| | 同步 | 异步 |
|---|---|---|
| 超时 | **一般几分钟**，超时即失败 | **立即确认请求**，之后**把结果 POST 到你提供的 webhook** |
| 时间尺度 | 分钟 | **通常以小时计而非分钟计** |

> **"配合强力的服务端队列，异步请求让高吞吐、延迟不敏感的系统更健壮、更高效。"**

### 5.4 流式与协议

**为什么文本够用而语音视频需要别的**：

> **"流式让应用感觉瞬间响应。对语言模型，通过 HTTP 流式输出文本就够了。但对其他模态，尤其是实时语音和视频，【输入和输出两个方向都需要能承载更多数据】。"**

**两个协议对比**：

| | **WebSockets** | **gRPC** |
|---|---|---|
| 适合 | **不需要强 schema 约束**的流式场景 | **定义良好的服务间通信** |
| 数据 | **非结构化、实时数据**（如音频），服务器收到后自己解析并下游处理 | **结构化数据，必须遵循预定义 schema** |
| 优点 | 灵活 | **省去解析输入的负担** |
| 缺点 | — | **多一层校验，所以略慢于 WebSocket** |
| 并发行为 | **服务器能支持固定且可配置的客户端数上限；达到上限时新连接无法建立，必须等空位或另一个副本扩起来** | 同左 |

> 💡 **"WebSocket 达到上限时新连接必须等待"这个特性，正好解释了 [08](08_多模态_语音与生成.md) 里 TTS 那条配置规则的必要性**——**为什么要"把 batch size 和活跃 WebSocket 数设成同一个值"**：因为**并发流数就是 batch size 的物理含义**，设得一致才能让利用率和稳定性同时成立。

## 6. 本章小结与自测

### 关键认知（我把可迁移的标了 ⭐）

**容器化**
1. **容器共享宿主内核**；三层结构（base + 附加 + **短暂的 container layer**）
2. **推理依赖链又长又脆，容器化是"保住已知可用构建"的手段**
3. **两条最佳实践：打包要轻 + 版本钉死**
4. **NIM 是"被替你做好的配置"，要最大控制权就自己从更少预设的 base 构建**

**自动扩缩**
5. **利用率是滞后指标，流量可前瞻；两者配合**——**prefill 的"少数超长请求"是高利用率但低请求数的典型**
6. **流量型扩缩五参数**：min/max replicas、window、scale down delay、concurrency target
7. **三种批处理**：static（等满，早期请求惨）< dynamic（加超时）< **continuous（token 级，延迟显著更低）**
8. **batch size ↑ → 吞吐 ↑ 但单用户延迟 ↑**；**concurrency target 要和副本 batch size 匹配**
9. ⭐ **扩缩判据：所有副本满并发 → 扩；很多副本跑半满 batch → 缩**
10. ⭐ **冷启动慢 → 不敢缩 → 过度配置**；四因素（GPU 采购/镜像/权重/引擎启动），**后三个是工程师能做的**
11. ⭐ **量化权重有额外好处：冷启动加载更快**
12. ⭐ **引擎缓存要求"GPU 型号、CUDA 版本、软件依赖完全一致"**——编译产物与目标环境强耦合
13. **路由回答"应该去哪"，负载均衡回答"可以去哪"**；**不能简单平均分配**（token 数差异大）
14. **KV cache-aware / LoRA-aware 路由**；**新副本上线要立刻被队列看到，否则延迟尖峰**
15. **Scale to zero 的两个前提**：快冷启动 + 健壮队列；**延迟敏感的轻量无规律流量不适合**（说明还不该自建）
16. ⭐ **独立组件扩缩，但必须在同一集群**（跨集群 40ms × 5 步 = 1 秒 SLA 的 20%）

**多云**
17. **多云的四个收益**：容量、冗余、延迟、合规
18. **架构分 control plane（全局决策）与 workload planes（独立服务流量）**，保证互不影响
19. **采购三机制**：reserved（折扣、长周期）/ on-demand（贵）/ spot（可抢占）；**大规模用混合**
20. ⭐ **请求穿过一个时区约 5ms**（纽约→旧金山 15ms）
21. ⭐ **故障是常态**：Llama 3 的 16,000 卡跑 54 天发生 **419 次中断 = 每 5 万 GPU 小时一次**；**而单节点跑一年就超 7 万 GPU 小时**
22. **GPU 健康是节点级问题**；做法：记录、隔离节点、轮换 pod
23. **最省事的安全改善：不存用户输入输出**（缩小攻击面）
24. **数据驻留**可以用多集群解决（加拿大数据留加拿大）

**测试与部署**
25. **三种测试**：手动 / 负载 / **影子流量（最好，先用抽样省钱）**
26. **蓝绿不适合大推理**（要双倍 GPU）；**金丝雀是推荐做法**（四步爬坡）
27. ⚠️ **金丝雀期间要确保新部署有足够活跃副本**，否则用户看到延迟尖峰
28. ⭐ **成本方法论：把 token 价格换算成总成本再比，别反推每 token 价格**
29. ⭐ **成本估算用至少一周的长周期**；**别忘了工程时间成本（TCO）**
30. **可观测七个指标，且要一起看**（延迟尖峰可能来自请求量，也可能来自长输入序列）
31. **可观测性必须和现有工具集成，不能孤立**

**客户端**
32. ⭐ **建立会话要几十毫秒；300ms 的 P95 SLA 里 TLS 握手占掉 10%**
33. **异步推理：立即确认 + webhook 回调，时间尺度从分钟变小时**
34. **WebSocket（非结构化，略快）vs gRPC（结构化，多一层校验）**
35. **WebSocket 有固定并发上限**——这解释了 TTS 那条"batch size = 活跃 WebSocket 数"的规则
