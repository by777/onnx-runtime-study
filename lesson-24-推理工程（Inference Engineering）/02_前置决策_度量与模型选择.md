# 02 前置决策：度量与模型选择

> **对应原书**：Chapter 1: Prerequisites
> **本课定位**：动手优化之前的那些决定。核心命题一句话：**推理优化是产品问题的答案，不是技术问题的答案。**

---

## 1. 核心命题：优化 = 在约束下找平衡

作者用了个我很喜欢的类比：

> NFL 球员又高又快又壮，但他们**不如相扑选手高、不如短跑运动员快、不如举重运动员壮**——因为他们的身体是为**这个位置上的整个赛季**优化的，不是为单项纪录。

推理系统同理。所以：

$$ \text{优化} \ne \max(\text{单一指标}) \qquad \text{优化} = \text{在约束下找平衡} $$

**动手之前要能回答五个问题**：

| 问题 | 内容 |
|---|---|
| Model requirements | 要跑哪个/哪些模型？ |
| Application interface | 输入怎么进来、输出要什么格式？ |
| **Latency budget** | 端到端要多快？ |
| **Unit economics** | 每请求/每用户/每月能花多少？ |
| Usage patterns | 多少并发？有没有时间段规律？ |

**作者的实用建议**：早期这些答案往往不清楚，**这时应该用现成的按 token 付费 API，而不是投资自建推理**。等产品规模化、需求清楚了，自建才值得。

> 💡 **这条对你有特殊意义**：你现在做的是"帮公司把模型部署到端侧"，本质是**专用部署**。理解"什么时候不该自建"能让你在技术选型会上说清楚成本边界，这是从工程师往上升的必备视角。

## 2. 共享推理 vs 专用部署

| | **共享**（按 token 付费） | **专用**（按 GPU 小时付费） |
|---|---|---|
| 优势 | 零开销、只为用量付费<br/>无冷启动、模型always可用<br/>工程投入最小（只需 API key） | 成本可控<br/>可定制/微调模型<br/>可满足特定延迟与可用性要求 |
| 劣势 | **成本随用量线性增长**<br/>**供应商可用性封顶你的可用性**<br/>"吵闹邻居"问题<br/>**对延迟/质量/限流无控制权** | 工程面积大增<br/>月支出下限提高 |

**转专用的三个理由**：规模、专精、编排。

作者的态度很克制：**"只有出现明确且即时的业务需求时才切换。"**

> ⚠️ 一个容易混的点：作者特意说明 **"共享 vs 专用"和"闭源 vs 开源"不是同一件事**——有很多开源模型的共享端点，也有很多闭源模型厂商给大客户提供专用方案。但**采用开源模型的一个关键动机，就是它能解锁不受限制的专用部署。**

## 3. 关于你的应用

### 3.1 八类 AI 原生应用与各自的考量

| 类别 | 例子 | 核心考量 |
|---|---|---|
| Agents | 销售线索挖掘 agent | **一个用户动作触发大量推理调用** |
| Chat | 带 RAG 的客服 | **TTFT 决定"感觉快不快"** |
| Voice | 实时翻译 | **端到端延迟决定对话是否自然** |
| Media | 虚拟试穿 | 在输出质量与速度间平衡 |
| Search | 法律文档发现 | **离线填语料 vs 在线用户请求**（两种负载） |
| RecSys | 电商推荐 | 高请求量下的一致延迟 |
| Completion | IDE 代码补全 | **在用户打字速度内出完整一段** |
| Moderation | UGC 安全扫描 | 高吞吐以压低单次检查成本 |

**这张表的价值**：它告诉你"延迟预算"不是抽象数字，而是**由应用形态决定的**——补全要跟上打字速度，语音要像对话，agent 一次动作可能触发几十次调用。

### 3.2 在线 vs 离线

**这是推理工程最根本的一组权衡**：

$$ \text{低延迟} \leftrightarrow \text{高吞吐} $$

| | 在线 | 离线 |
|---|---|---|
| 特征 | 有真人在等 | 批量任务 |
| 该优化 | **延迟** | **吞吐** |
| 例子 | 代码补全、chat、语音 agent | 播客转写归档、文档处理、语料准备 |

**一个反直觉的实操结论**：如果同一个模型（比如 Whisper）两种流量都够大，**建两个部署比共用一个更省钱**——一个为延迟优化，一个为吞吐优化。

> 💡 **这正是"约束越多性能越好"的应用**：同一个模型拆成两个受约束的部署，总成本反而低。

### 3.3 消费级 vs B2B

| | 消费级 | B2B |
|---|---|---|
| 成本敏感度 | **很高** | 较低（毛利更好） |
| 流量可预测性 | **差**（可能一夜爆红） | 好 |
| 优先级 | **边际成本 + 灵活性**<br/>（延迟和可用性保持"体面"标准即可） | **延迟 + 可用性**<br/>（成本规模是次要关切） |

**合规的三个问题**（作者点名要和法务/安全一起看）：

1. **数据主权**：你的 GPU 所在的司法区域，允许接收用户数据吗？
2. **用户隐私**：模型的输入输出是否保持私密安全？
3. **监管合规**：你和你的下游供应商都合规吗？

> 💡 **对你直接相关**：你在移远做语音链路（KWS/ECNR），语音是**最敏感的数据类型之一**。原书 [04 硬件](04_硬件_GPU与本地推理.md) 3.5.2 节会强调"on-device 的价值是数据不出设备"——**这两处合起来就是端侧部署的合规论证**。

## 4. 模型选择：全书最重要的一个决定

作者的主张非常直白：

> **模型性能优化里最重要的决定，不是选运行时引擎、不是选推测算法，而是你一开始选了哪个模型。**

逻辑很朴素：

$$ \text{同等条件下（硬件、运行时、优化、架构），参数少的模型一定更快更便宜} $$

### 4.1 分阶段的建议（这是最实用的部分）

| 阶段 | 建议 |
|---|---|
| **PMF 之前**（产品市场契合前） | **别自己搞推理**。直接用按 token 付费的前沿模型 API（Kimi、DeepSeek，甚至 GPT/Gemini）。"在找到 PMF 之前，不值得在自建推理上花时间和钱。" |
| **要规模化时** | **反过来**——找（或造）**能完成任务的最小的、最容易跑的模型** |

作者诚实地补了一句：很多时候这个"最小的模型"其实还是万亿参数的前沿模型，**但永远值得先检查一下更小更便宜更快的模型能不能胜任。**

**还有一条容易被忽略的工程约束**：选哪个模型也决定了你能用哪些优化——**推理引擎对不同架构的支持深度不同**。所以**尽量用流行的模型架构**，以保证在整个性能工具链里都能得到良好支持。

### 4.2 微调（Fine-tuning）

**定义**：拿一个预训练基座模型，用新数据适配到特定用例——**改变权重的值，但架构不变**。

**为什么对推理重要**：**"如果你能把一个小模型微调到通过你的评测，你就为自己铺好了更容易命中延迟和成本目标的路。"**

作者举的例子（text-to-SQL）值得记：

| | 通用代码模型 | 微调后的小模型 |
|---|---|---|
| 参数量 | 几百亿 | **几亿**（差 2 个数量级） |
| 任务表现 | 会写 SQL | **在这个特定任务上等效** |
| 为什么可行 | — | **SQL 是约束很强的语言** + 干净的领域边界 + 好的评测标准 + 高质量标注数据 |

作者也很诚实：**"text-to-SQL 是个极端的例子，很多领域支撑不了这么大的模型缩减"**——但它是说明"干净领域 + 强评测 + 好数据"能带来什么的范例。

### 4.3 蒸馏（Distillation）

**与微调的区别**（这是关键）：

| | 微调 | 蒸馏 |
|---|---|---|
| 训练信号 | 输入-输出**对** | **teacher 的完整概率分布**（不只是最终答案） |
| 教什么 | "在这个领域做得更好" | **"模仿大模型的行为——好的和坏的都模仿"** |

**一个被戳破的误解**（作者专门说了）：

> 前沿实验室发布不同尺寸的模型家族时，**小模型通常不是从大模型蒸馏的**，而是**独立训练**的——目的正是**防止大模型的偏差人为限制小模型的能力**。

**那蒸馏什么时候有用**：当实验室**只训了大模型**时，蒸馏能让它更可及。典型例子是 **DeepSeek-R1**：671B 太大，于是他们在大模型基础上，对当时最流行的开源架构（**Llama 3 和 Qwen 2.5**）出了蒸馏版。蒸馏版**推理行为相似、智力基准分数差一些，但小得多且能复用已有架构的性能优化工作**。

> 💡 **蒸馏的业务价值 = 复用成熟架构的优化生态**。这个视角比"小模型更便宜"更深刻。

### 4.4 评测（Evals）—— 一段清醒话

**评测是推理工程的前置条件**，两个作用：

1. **明智地花时间**：投入优化之前，先确认模型是有用的
2. **建立基线**：有些优化技术有损质量，需要基线来对照

作者对公开基准的批评很直接：

> 标准智力基准（MMLU、SWE-bench）用来**初筛**模型有用，但它们**已经饱和甚至被"刷"了**。引 Goodhart 定律：**"当一个度量变成目标，它就不再是好度量。"** 而前沿实验室有强烈动机每次发布都秀世界纪录。

更可靠的替代：**Elo 评分（head-to-head 胜率）**。但作者的核心主张是：

$$ \text{没有东西能替代——直接测量模型在你应用上的表现} $$

三条实操建议：**看你的数据**（对照产品直觉检查评测结果）、**精确**（清楚模型要解的最难的问题，聚焦在那里）、**用工具**（别重新发明 AI 工程里的基础轮子）。

> 💡 **这条对你面试极有用**：如果你被问"你怎么知道量化后模型还能用"，答案就是这个框架——**不看公开榜单，跑你自己的最难 case，对照未量化基线**。[06 量化](06_量化_动态范围与粒度.md) 会展开三种验证方法。

## 5. 延迟与吞吐的度量 —— 术语定义章

### 5.1 两个基础指标

| | **TTFT**（Time To First Token） | **TPS**（Tokens Per Second） |
|---|---|---|
| 含义 | 流式输出下，用户看到第一个 token 要多久 | 首 token 之后，用户每秒收到多少 token |
| 底层 | **compute-bound 的 prefill** | **bandwidth-bound 的 decode** |
| 优化方向 | 越低越好（延迟） | 越高越好（延迟） |

**TPS 有歧义**——作者专门澄清，并给了三个更精确的说法：

| 术语 | 含义 | 类型 |
|---|---|---|
| **Perceived TPS** | 首 token 之后单用户观察到的每秒 token 数 | **延迟** |
| **Total TPS** | 整个服务每秒生成的总 token 数 | **吞吐** |
| **ITL**（Inter-Token Latency） | 相邻 token 的时间间隔 | 延迟（**10ms 间隔 ≈ 100 token/s**） |

> ⚠️ **别混**：大多数人说 TPS 指的是**单用户延迟**。写文档/做汇报时用精确术语，否则会误导。

**什么场景用 TTFT/TPS，什么场景不用**：它们主要用于**面向用户、流式输出的 LLM 系统**（聊天）。**如果是 agent 的工具调用，token 单独没有意义，应该直接看总响应时间。**

> 💡 **对照你的术语表 11.2**：你已经有 TTFT/TPOT/ITL/RTF 了。这里可以补一条对应关系：
> **TTFT ↔ prefill ↔ 算力受限**，**TPOT/ITL ↔ decode ↔ 带宽受限**。你表里已经写了"两阶段两纪律"，本课 [03](03_模型机制与瓶颈计算.md) 会给出这个对应关系的**定量证明**。

### 5.2 延迟要看百分位，不要看均值

**为什么**：LLM 总响应时间是**右偏分布**——大多数集中在某个众数附近，但异常值可以长得多。

作者的一句话我认为是所有性能工作的通用准则：

> **"如果每十次交互里有一次要等好几秒，那大多数交互很快也不够好。"**

| 百分位 | 含义 | 通俗说法 |
|---|---|---|
| P50 | 中位延迟 | 每 2 个请求有 1 个更慢 |
| P90 | 90 分位 | 每 10 个有 1 个更慢 |
| P95 | 95 分位 | 每 20 个有 1 个更慢 |
| P99 | 99 分位 | 每 100 个有 1 个更慢 |

**结论**：降低平均延迟重要，但好的性能工作**还要专门去压 P90/P99**，因为那才是用户信任的来源。

### 5.3 端到端 vs 纯推理指标

| 指标类型 | 包含什么 | 告诉你什么 |
|---|---|---|
| **inference-only** | 只有 GPU 上生成 token 的时间 | **你的模型性能优化有没有效** |
| **end-to-end** | 加上网络延迟、排队时间 | **用户感知有多快** |

**最重要的一条诊断规则**：

$$ \text{推理快 且 端到端慢} \;\Longrightarrow\; \text{去查基础设施，别再优化模型性能了} $$

> 💡 **这条规则很值钱**。它把"该优化 runtime 还是优化 infrastructure"这个容易搞错的分流问题变成了一次判断。你的场景（端侧）也一样适用：**NPU 推理 1300us 但端到端卡顿 → 去看数据搬运/前后处理，不是去压 NPU。**

## 6. 本章小结与自测

### 关键认知

1. **优化不是最大化单一指标，是在约束下找平衡**——"NFL 球员"类比
2. **PMF 之前别自建推理**；规模化时反过来找**能完成任务的最小的模型**
3. **最重要的一步是选模型**，不是选引擎或算法
4. **微调改权重的值，蒸馏教模型模仿 teacher 的概率分布**——后者能让大模型"更可及"并**复用成熟架构的优化生态**
5. **公开基准会饱和和被打磨**，要跑**你自己最难 case** 的自定义评测
6. **TTFT ↔ prefill ↔ 算力受限；TPS/ITL ↔ decode ↔ 带宽受限**
7. **看百分位不看均值**——"每十次有一次要等好几秒，大多数很快也不够"
8. **推理快但端到端慢 → 查基础设施，不是压模型**

### 自测

- [ ] 你的 KWS/ECNR 部署算在线还是离线？该优化延迟还是吞吐？
- [ ] 如果老板问"为什么我们不自己搭服务而用现成方案"，你能用"共享 vs 专用"的六条优劣回答吗？
- [ ] 你的项目的 P99 是多少？（如果答不上来，这本身就是个可做的改进）
- [ ] 你手上有"自定义评测集"吗？没有的话，怎么造一个？
