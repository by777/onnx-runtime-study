## 0. 这一章要回答的问题

> GPU 上有两个资源——**算力**和**内存带宽**。现实中总有一个饱和、另一个闲置。

如果你只知道一句话，就记这句：**如果一个操作是内存带宽受限的，那么无论怎么优化算力都不会让它变快——你可以把 FLOPS 翻倍，然后测出零变化。**

## 1. 神经网络最小必要知识

### 1.1 结构与两种网络

- **节点（neuron）**：一小段程序，输入 × 权重 + 偏置，返回结果
- **层**：一组节点，**同层节点互相独立**
- **网络**产生在层与层之间：本层节点接收上一层的输出
- 三种层：**输入层 / 隐藏层 / 输出层**；隐藏层的输出叫**隐藏状态**
- **维度**是内部表示的关键属性：文本输入要**升维**（几百到几千个数的向量以捕捉语义）；图像模型要**降维**（从百万像素降到可管理的尺寸）

两类网络：
- **Encoder**：把输入（文本/图像）编码成带额外信息和语义的内部表示
- **Decoder**：用内部表示生成输出（文本/图像）

| 架构 | 现状 |
|---|---|
| decoder-only | 现代 LLM 都是这种 |
| encoder-only | **今天比较少见**，代表是 BERT 家族的老式文本 embedding 模型 |
| **encoder-decoder** | **很多其他模态用这个**——Whisper（音频转写）就是 encoder 处理音频、decoder 生成文本 token |

### 1.2 matmul 是核心操作

**线性层 = 最简单的 matmul**：

$$ y = Wx + b $$

> 💡 **跟你 T41 的呼应**：你的 NNMAC 矩阵计算、tile 切分、WRAM/FRAM 片上存储，服务的正是这个操作。**整个神经网络推理 = 一长串 matmul + 少量非线性**。这也是为什么 [05](05_软件栈_CUDA到推理引擎.md) 会说 GEMM 是最重要的 kernel。

### 1.3 为什么需要激活函数（这个推导值得看懂）

**矩阵乘法是可复合的**（composable）：

$$ W_2(W_1 x) = (W_2 W_1)\, x $$

**这是个问题**：如果多层网络每层都是 matmul，那么**整个网络会坍缩成一个"所有矩阵相乘"的单层**——深度就白搭了。

而深度网络有用的原因恰恰是**更多层能有效利用更多参数、在隐藏状态里编码更多含义**。

所以需要用**激活函数**来打断线性：

- **非线性**——防止可复合的 matmul 把层坍缩
- **（大体）可微**——支持反向传播

**ReLU**（Rectified Linear Unit，修正线性单元）是最基础的之一：$x > 0$ 返回 $x$，否则返回 0。
还有几十种（包括因为像 Nike logo 而得名的 **Swish**），但**大多数遵循同一模式：把负值映射到零或近零，正值保持不变**。

常见的有 **ReLU、SiLU、Swish、SwiGLU**，共同特点：**跑得快、好训练（大体可微所以大多数点有梯度）、能打断线性以支撑多层网络**。

## 2. LLM 推理机制

### 2.1 token 与词表

- LLM 是**自回归 token 生成**模型：**基于此前所有 token 一次生成一个新 token**
- **subword tokenization**：一个 token = 一个词或词的一部分。常见词和标点各占一个 token，不常见的词拆成多个
- **分词不需要神经网络**——tokenizer 只是字符串 ↔ 数字 token 的映射
- **词表** = token 与字符串的完整映射，**大多数模型 10 万+ token**
- **效率影响**：生成同样输出所需的 token 越少，端到端推理越快
- 其他模态会**扩展词表**让 token 表示别的东西（比如音频波形）

### 2.2 三类序列与上下文窗口

| 序列 | 内容 |
|---|---|
| **Input sequence** | prompt、chat、context、functions 等 |
| **Reasoning sequence** | 推理模型可选的中间"思考"输出 |
| **Output sequence** | 模型生成的响应 |

三者合计受**上下文窗口**限制（单请求能处理+生成的总 token 数）；请求还可以用 `max_tokens` 进一步限制输出长度。

**一个容易被忽略的工程细节**：输入虽然概念上是单字符串，但 LLM 被训练来接受**多轮对话（带角色）、工具调用的函数签名、有时还有多模态输入**。这些都要拼成单一序列——由 **chat template** 处理，**它逐模型有细微差别，必须在推理引擎里实现正确**。

### 2.3 两个阶段（全书最重要的划分）

```
token 化输入（套用 chat template）  ← 推理的第 0 步
        ↓
Prefill：处理输入序列，为每个输入 token 算 attention，存进 KV cache
        ↓
Decode：反复前向，自回归生成 token
```

### 2.4 decode 里的 token 是怎么选出来的

神经网络输出的是**向量不是 token**，所以 decode 多几步：

1. 输出层产出 **logits 向量**，**长度 = 词表大小**
2. 归一化后，logits 表示**词表里每个 token 是正确输出的概率**
3. 按归一化概率向量**加权随机数生成**选出输出 token

**三个调节旋钮**：

| 参数 | 作用时机 | 效果 |
|---|---|---|
| **Temperature** | 归一化**前**调整 logits 本身 | 低 → 更可预测 |
| **Top-k** | 归一化**后**取最可能的 k 个，再重新归一化 | k=1 → 确定性 |
| **Top-p** | 取累积概率达到 p 的**最小集合** | 低 → 更可预测 |

**temperature=0 或 top-k=1 就变成确定性的**（永远选概率最高的 token）。

**结构化输出**（输出要符合 JSON 之类 schema 时）还有 **logit biasing** 等工具，**每次前向后应用**，支撑**工具调用**等重要能力——**它们的实现正确性对高质量推理是必需的**。

**循环终止**：直到模型生成 **stop token**（特殊值，标志输出序列结束），或者先撞上上下文窗口/max tokens 限制。

### 2.5 读架构名（实用技能）

`Qwen3MoeForCausalLM` 拆开看：

| 部分 | 含义 |
|---|---|
| Qwen | 模型家族（品牌） |
| 3 | 家族内架构大版本 |
| **MoE** | 是 Mixture of Experts 模型 |
| **CausalLM** | 因果语言模型 |

**causal LM** = 基于此前 token 预测下一个（对比 masked LM 是"根据左右两边填空"）。**今天所有生成式 LLM 都是 causal LM。**

**架构 vs 尺寸 vs 变体 vs 微调**（容易混）：

| 概念 | 例子 | 说明 |
|---|---|---|
| 架构 | Llama | 训练过程中对每个组件的性质和形状所做决定的总和 |
| 尺寸 | Llama 8B / 70B | 同一架构不同参数量 |
| 变体 | base / instruct | 同一架构，行为不同 |
| 微调 | LoRA | **改变行为，不改变架构** |

**为什么架构重要**：它决定 runtime 和引擎支持。**如果你有某个架构的高度优化部署，那么同架构的另一个变体也能享受同样的性能改进。**

### 2.6 Transformer block 内部

三层结构：

| 层 | 作用 |
|---|---|
| **Embedding layer** | 输入层，token → embeddings |
| **Transformer blocks** | 隐藏层，生成预测 |
| **Output layer** | 也叫 LMHead（language modeling head），把隐藏状态转成 logits 向量（每个词表 token 一个） |

block 内部的子层：**attention + 前馈网络（FFN）+ normalization**。

**一个关键的权重分布事实**（这个数字很重要）：

$$ \underbrace{\text{FFN}}_{\text{占大头}} \;>\; \underbrace{\text{attention}}_{\text{第二}} \;\gg\; \underbrace{\text{normalization / 激活}}_{\text{舍入误差级别}} $$

FFN 是多层感知机（MLP）。**这些线性子层占 LLM 可训练权重的绝大部分，attention 子层是第二大组件。**

> ⚠️ 注意这里的张力：**线性子层占权重最多，但推理时更复杂的操作是 attention**。这个区分在 [06](06_量化_动态范围与粒度.md)（量化该先动哪部分）和 [08](08_多模态_语音与生成.md)（视频生成里 attention 占 70-80% 算力时间）会反复用到。

### 2.7 Attention

**作用**：transformer 用来把某个 token 与序列中其他 token 关联起来的机制。

作者的例子很好：句子 *"I decided to write a book because I thought it would be easy, but it was actually hard."* —— attention 让模型知道这里的 **"it" 指的是写书**。

**三个输入**：

| 输入 | 含义 |
|---|---|
| **Q**（queries） | **正在生成/更新**的那个 token 的嵌入表示 |
| **K**（keys） | **所有先前 token** 的表示 |
| **V**（values） | 所有先前 token 算出的 attention 值 |

**Multi-head**：注意力子层是多头的，**每个头是一次独立的 attention 操作**，在架构图上是同一子层里的并行分支。**每个头可能负责不同类型的关系**，比如主谓一致、指代消解。

**两种 attention**：

| 类型 | 特征 | 用在哪 |
|---|---|---|
| **Self-attention** | Q、K、V 来自同一序列 | LLM（**外加因果掩码**防止偷看后面） |
| **Cross-attention** | Q 来自**不同**序列，用外部信息给 Q 做条件 | 图像生成、多模态（图像 ↔ 文本 prompt） |

**复杂度问题与 KV cache**：

$$ \text{attention 本身} = O(N^2) \quad\xrightarrow{\text{KV cache}}\quad \text{实践中} = O(N) \text{（线性）} $$

attention 要拿当前 token 和**每一个先前 token** 找关系，所以对序列长度是**二次时间**——"**随着上下文扩张，attention 变慢**"。

**但实践中 attention 是线性的，因为 KV cache**：它是 attention 实现的标准组件，为每个先前 token 存 key-value 对。**靠查 KV cache 而不是每次重算，attention 就跑在线性时间。**

**KV cache 的生命周期**：**prefill 阶段建立 → decode 阶段使用并更新 → 默认活在 GPU 显存里**。存储、访问、复用它（[07 缓存](07_投机_缓存_并行_拆解.md)）是推理工程的大主题。

> 💡 **这是全书的枢纽概念**。KV cache 同时是：prefill 的产物、decode 的依赖、显存的主要消耗者（权重之后 80%+ 余量）、量化的第三敏感组件、prefix caching 复用的对象、disaggregation 要跨卡传输的数据。**看不懂 KV cache 就看不懂这本书的一半。**

### 2.8 MoE（Mixture of Experts）

**为什么要 MoE**：网络的"稠密度"由**层间连接数**决定——**越稠密保留信息越多，越稀疏跑起来越省算力和内存**。MoE 就是**给线性层加稀疏性**的架构优化。

**做法**：不是一个大矩阵，而是**几百个更小的矩阵（专家）**，**每个输入只路由到少数几个专家**（这叫"激活专家"）。

**关键数字**（例子很直观）：

| 模型 | 总参数 | 每请求激活 | 专家数 | 层数 | 每 token 每层选 |
|---|---|---|---|---|---|
| Qwen3-235B-**A22B** | 235B | **22B** | 128 | 94 | **8 个专家** |

**由此得出一个重要的双面结论**：

| 场景 | MoE 表现 |
|---|---|
| **单请求本地推理** | **非常高效**（激活参数少） |
| **生产服务器批处理** | ⚠️ **"不同请求激活不同专家，你应该预期任何时候几乎全部参数都是活跃的"**——除非通过大规模**专家并行**真正实现稀疏 |

**粒度很细**：router（LLM 内部的一个小模型）**在每一层为每个生成的 token 挑选专家**。上例：94 层 × 每层选 8 个专家（从 128 个里）。

**适用边界**：
- **100B+ 参数的大模型**特别流行 MoE
- 也有 20-30B 的小 MoE
- **32B 以下（尤其 8B 以下）用传统稠密架构更高效**
- 领域特化模型（如代码补全）从 MoE 获益不多——**因为整个模型实际上就是一个专家**

**MoE 引入的新能力**：**Expert Parallelism（专家并行）**——让大模型在多 GPU 上高吞吐推理（详见 [07](07_投机_缓存_并行_拆解.md)）。

## 3. 图像生成机制

### 3.1 不是一个模型，是一条流水线

图像生成模型**不像 LLM 那样是单体模型**，而是**多个模型协同的流水线**。三个必备组件：

| 组件 | 作用 |
|---|---|
| **Text encoder** | 把文本 prompt 转成图像模型能懂的指令 |
| **Denoising model** | **核心**，从噪声迭代到图像 |
| **VAE**（Variational Autoencoder） | 把模型输出从 latent space 转回像素空间 |

**流水线思维延伸到生态**：基础模型之外还有 **LoRA**（轻量微调，改风格和质量）和 **ControlNet**（用轮廓和边缘引导输出匹配大致形状/颜色）。开源生态里 **ComfyUI** 这类工具用于组装复杂流水线、替换组件。

### 3.2 为什么必须在 latent space 里算

普通 HD 图像 1024×1024 = **一百多万像素**。denoising 模型**需要对整张图并行算 attention**——在像素空间做不可行。

**latent space 是图像的低维表示**：一张图的 latent 矩阵可能是 **128×128，约为其表示的像素空间总值的 1%**。

### 3.3 迭代去噪的两个关键事实

```
latent 初始化为随机值（噪声）
   ↓ 基于文本 prompt，用 denoising model 逐步精炼
每一个 step 更新【整个】latent  ←← 不像 LLM 是一次一个 token
   ↓ 通常 30-50 步
高质量图像
```

**数数陷阱（重要）**：**每一步跑两次前向**——一次**带条件**（文本 prompt）、一次**不带条件**，然后按 **guidance scale** 合并。

$$ \text{50 步} \;\Longrightarrow\; \text{实际上 100 次前向} $$

> 💡 这个"×2"是 [08](08_多模态_语音与生成.md) 那个"奇怪的技巧"（后半程关掉 guidance）能省 20% 前向的**前提**。

### 3.4 请求级参数

| 参数 | 作用 |
|---|---|
| **Prompt** | 描述图像应该长什么样 |
| **Negative prompt** | 单独描述**不应该**出现的风格或物体 |
| **Number of steps** | 在速度和质量间权衡（多数模型 30-50） |
| **Guidance scale** | 控制**创造力 vs prompt 遵循度**的平衡，整数，一般约 **4** |
| **Image size** | 从固定菜单里选分辨率和宽高比 |

### 3.5 架构演进：一个很有说服力的对照

**diffusion transformer**：和 LLM 用的 transformer 非常像，区别是**处理图像数据而不是离散 token 的嵌入**。图像按 **2×2 或 4×4 的重叠 patch** 喂进去，嵌入到 latent space；推理方向相反，生成结束时 latent 转回像素。

**SDXL（2023）vs Qwen Image（2025）**——这张表解释了能力跃升的来源：

| 组件 | SDXL (2023) | Qwen Image (2025) |
|---|---|---|
| Text encoder | 基于 CLIP 的模型 | **Qwen 2.5 VL（7B）** |
| Denoiser | <4B 参数 | **20B 参数** |
| VAE | 单编码 | 双编码 |

**作者的归因很清楚**：能力大幅增长来自**更大的组件模型 + 更复杂的流水线**。新能力（可读的文字渲染、逼真人脸）来自两件事：

1. **文本编码从小 NLP 模型换成完整 LLM**
2. **denoiser 参数量涨了 5 倍**

**前沿方向：把扩散 transformer 和 LLM 架构混起来**。作者给的理由很漂亮：

> **任何能被 token 化的东西都能建模成 LLM。**

LLM 的优势：**内置的文本理解 + 本身就是图像生成流水线的重要组件**。而且 LLM 解决了扩散模型的两个固有局限：

| 局限 | 扩散模型 | LLM 风格 |
|---|---|---|
| 输出尺寸 | 固定 | **自回归，可变长度** |
| 生成代价 | 最多 100 次前向 | **单次前向出 token** |

代表：**HunyuanImage-3.0**。

### 3.6 Few-step 模型

**思路转换**：与其让每步更快，不如**用更少的步数**。

- 训练目标：**8 步以内**出高分辨率图像
- 收益：**开箱比传统模型快 80-90%**
- 代价：**输出质量明显下降**

两条路线：

| 方法 | 做法 |
|---|---|
| **Latent consistency** | 训练模型**直接预测目标 latent 向量**，重复 2-4 次预测以增强质量 |
| **Distillation** | 用对抗蒸馏和/或渐进蒸馏，训练小模型**在更少步数内模仿大模型** |

**今天蒸馏比 latent consistency 更常见**：新模型（FLUX、Qwen Image）发布时，社区除了出质量和风格 LoRA，还会出蒸馏版。

**选型建议**：**延迟敏感且质量不太重要的场景**（如实时生成滤镜）才考虑 few-step 模型。

### 3.7 视频生成

**架构上和图像生成相似，只是更大**：

| 维度 | 倍数 |
|---|---|
| 参数量 | **3-5 倍** |
| latent 编码信息量 | **10-100 倍** |

**为什么不能逐帧生成（早期的错误做法）**：

```
逐帧：先生成起始帧 → 用它生成下一帧 → 再下一帧 ...
问题：误差累积——早期的小问题逐帧复合，视频很快"跑偏"
```

**现代做法**：**把整个视频放在 latent 里**，**每个去噪步都修改它**，**每一帧都 attend 到其他所有帧，且每次前向都被更新**。

**latent 空间的维度差异**：

$$ \text{图像} = (X, Y) \qquad\qquad \text{视频} = (X, Y, T) $$

**主要限制**：

- 视频帧数是**固定的**（就像图像模型有固定宽高比），现代模型生成**几秒**的序列
- **真正的约束是算力**：即使在最新 GPU 上，**对巨大 latent 空间的 attention 极其昂贵，每生成一秒视频要好几秒推理**
- **算力密集到通常 batch size = 1**——**一整个 8 卡节点在处理一个请求**

**步数与图像相同**（一般约 50 步），**但每步处理的数据多得多**。

**一个很妙的对照表**（说明视频生成今天的处境）：

| LLM（2023 末） | 视频生成模型（2025 末） |
|---|---|
| 高 TTFT、低 TPS | 生成慢 |
| 频繁幻觉 | 物理不真实 |
| 吃满 Ampere GPU | 吃满 Blackwell GPU |
| 上下文窗口有限 | 视频输出很短 |

**作者的点**：这些限制**今天在 LLM 上基本已被消除**，把它们从电影级视频生成（以及 world model、3D 物体生成等）里消除是**非常活跃的研究领域**。

## 4. 瓶颈计算 ⭐⭐ —— 本章核心

### 4.1 两个资源

| 资源 | 单位 | 含义 |
|---|---|---|
| **Compute** | FLOPS | GPU 每秒能做的浮点操作数 |
| **Memory bandwidth** | bytes/s | GPU 每秒能搬多少字节 |

**理想世界**：算力从不空等内存，带宽从不空等算力。
**现实世界**：存在 **bottleneck（瓶颈）**——一个资源闲置而另一个饱和。

**"发现这些瓶颈是提升性能的第一步。如果一个操作受限于内存带宽，那么无论如何优化算力都不会让系统变快，反之亦然。"**

### 4.2 三条结论（先背下来）

| 场景 | 瓶颈 |
|---|---|
| **LLM prefill**（构建 KV cache） | **compute bound** |
| **LLM decode**（生成 token） | **memory bound** |
| **图像和视频生成** | **compute bound** |

**优化目标不是"消除瓶颈"，而是"让瓶颈不那么限制系统整体性能"**。作者给的例子：**把多个请求 batch 起来，让 LLM decode 不那么内存受限——因为处理一批请求用同样的内存流量做了更多计算。**

### 4.3 ops:byte ratio（硬件属性）

$$ I_{ridge} = \frac{\text{GPU 峰值算力}}{\text{GPU 内存带宽}} $$

单位 **ops/byte**，含义是：**它必须每搬一个字节做多少次操作，才能让两个资源都保持忙碌。**

**算例（H100 FP16）**：

$$ I_{ridge} = \frac{989\ \text{teraFLOPS}}{3.35\ \text{TB/s}} \approx \mathbf{295\ ops/byte} $$

> 💡 对照你的 [技术名词表 11.3](../技术名词表.md)：这个 295 你已经有了。**本章补充的是"怎么用它做判断"和"案例数字"。**

### 4.4 算术强度（算法属性）

$$ I = \frac{\text{总运算量（ops）}}{\text{总内存流量（bytes）}} $$

**也叫 operational intensity**。

**两者单位口径的差别要注意**：
- **ops:byte 是每秒尺度**测的（硬件能力）
- **算术强度是单次函数/算法执行**累计测的（算法需求）

### 4.5 roofline 判据

```
性能
  ↑
  │                    ┌──────────────────────  ← 算力上限（水平线）
  │                   ╱
  │                 ╱      ← 带宽上限（对角线）
  │               ╱
  │             ╱
  │           ╱
  │         ╱
  │       ╱
  └──────────────────────────────→ 算术强度 I
         ↑
      ridge（交点）
```

| 条件 | 结论 | 该做什么 |
|---|---|---|
| $I > I_{ridge}$（撞到水平线） | **compute bound** | 加带宽没用 → **降精度 / 换更快 kernel** |
| $I < I_{ridge}$（撞到对角线） | **memory bound** | **加算力没用** → **减少搬运 / 提高数据复用** |

**找瓶颈的方法**：对着系统里**最贵的那些计算**算它们的算术强度。**对推理来说，其中一个就是 attention。**

### 4.6 为什么 prefill 算力受限、decode 带宽受限（定量证明）

**两者的根本差别**：

| | 处理方式 | 为什么 |
|---|---|---|
| **Prefill** | **并行处理整个输入序列** | 权重**加载一次**，然后在输入矩阵与 attention 矩阵之间做**一系列大矩阵乘法** → **大量计算对一次读取** → 高算术强度 |
| **Decode** | **一次生成一个 token** | **每个 token 都要重新加载模型权重**，但只用来做**代价小得多的向量-矩阵乘** → **相对很少的浮点操作对加载整个权重** → 低算术强度 |

**具体算例（原书的推导，我按它的参数重算并核对过）**

参数设定：**d = 128**（attention head 维度）、**N = 4096**（序列长度）、**FP16**（每值 2 字节）。

矩阵尺寸：

| 矩阵 | 尺寸 | 说明 |
|---|---|---|
| Q, K, V | $N \times d$ = 4096×128 | |
| S, P | $N \times N$ = 4096×4096 | 注意力分数与概率矩阵 |
| O | $N \times d$ = 4096×128 | 输出 |

> 顺带一个量感：**一个 4096×4096 的矩阵约 32 MiB**，**大约相当于一张高分辨率 RAW 单反照片的数据量**。

标准 attention（无优化）三行伪码，**每行都是"从内存加载 → 计算 → 存回内存"**：

```
S = Q @ K.T          # step 1
P = softmax(S)       # step 2
O = P @ V            # step 3
```

**内存流量统计**（单位：元素个数）

| 步骤 | 读 | 写 |
|---|---|---|
| 1. $S = QK^\top$ | Q $Nd$ + K $Nd$ | S $N^2$ |
| 2. $P = \text{softmax}(S)$ | S $N^2$ | P $N^2$ |
| 3. $O = PV$ | P $N^2$ + V $Nd$ | O $Nd$ |
| **合计** | $3Nd + 2N^2$ | $2N^2 + Nd$ |

$$ \text{总流量} = 4Nd + 4N^2 = 4 \times 4096 \times 128 + 4 \times 4096^2 = 69{,}206{,}016 \ \text{元素} $$

$$ \text{换算成字节（FP16，2 B/元素）} = 138.4\ \text{MB} $$

**运算量统计**（两个 matmul 各 $2N^2 d$ FLOPs）

$$ \text{总运算} = 2 \times (2N^2 d) = 4 \times 4096^2 \times 128 \approx 8.59\ \text{GFLOP} $$

**算术强度**

$$ I = \frac{8.59 \times 10^9}{138.4 \times 10^6} \approx \mathbf{62\ ops/byte} $$

> 📌 **核对说明**：原书把这三个步骤的逐项读写和运算量表放在**图片**里（Figure 2.15-2.18），而 `pdftotext` 提不出图片内容。所以我按上面的参数**独立推导**了一遍，结果 **62 与原书正文明确写出的"62"完全一致**——说明推导口径对得上（原书只计两个 matmul 的 FLOPs，softmax 的约 $5N^2$ 量级可忽略，计入也只到约 63）。
> 想自己验算：`python3 roofline.py --gpu H100 --verify 62`

**结论**：

$$ 62 \;\ll\; 295 \quad\Longrightarrow\quad \text{decode 是内存受限} $$

作者诚实地指出：**这样算算术强度是学术练习，不是推理工程师的日常任务**——**但算一次对建立直觉很有用。**

#### 4.6.1 一个额外洞察：这个 62 不是"序列再长一点就能救"的

讲义里值得补一句原书没展开、但很容易被误解的事：

$$ \text{未融合 attention:} \quad I(N) = \frac{4N^2 d}{2\,(4Nd + 4N^2)} \;\xrightarrow{\;N \to \infty\;}\; \frac{d}{2} $$

因为**流量和运算量都随 $N^2$ 增长，$N$ 约掉了**——所以算术强度**收敛到一个常数上限 $d/2$**：

| 序列长度 N | 未融合 I | d=128 时的渐近上限 |
|---|---|---|
| 4096 | 62.1 | |
| 32768 | 63.8 | |
| $\infty$ | → **64** | **$d/2 = 64$** |

**$64 < 295$，所以未融合 attention 在任何序列长度上都是带宽受限。** 瓶颈不是"序列太长"，**是这种实现方式本身**。

**那 FlashAttention 到底砍掉了什么**？它**不落 S/P 中间矩阵**，于是流量只剩 Q/K/V 各读一次 + O 写一次（**$4Nd$ 元素，没有 $N^2$ 项**）：

$$ \text{融合后:} \quad I = \frac{4N^2 d}{2 \cdot 4Nd} = \frac{N}{2} \quad\Longrightarrow\quad \textbf{随序列长度线性增长} $$

| N | 未融合 I | 融合后 I | H100 上判定 |
|---|---|---|---|
| 512 | 51.2 | 256 | 带宽受限 |
| **591** | ~62 | **295** | **翻过分界点** |
| 4096 | 62.1 | **2048** | **算力受限** |
| 32768 | 63.8 | 16384 | 算力受限 |

> 💡 **这就是 FlashAttention 存在的量化理由**：它把"上限固定的常数 64"变成了"随长度增长的 $N/2$"。
> 一处 $N^2$ 中间矩阵的往返，决定了 attention 是永远带宽受限、还是长序列下算力受限。
>
> 这也解释了为什么原书说 **FlashAttention 对 compute-bound 的操作尤其有用**（prefill、视频生成）——**因为融合正是让它们变成 compute-bound 的那个动作**。

验算：`python3 roofline.py --gpu H100`（表格里同时给出融合前后的 I）

### 4.7 batching 的全部理由（这一节请精读）

**核心事实**：

> **70B 模型 FP16 意味着每生成一个 token 要从内存搬 140 GB。在 H100 上，光这一次读取就要约 42 毫秒——无论算术多快。**

$$ 70 \times 10^9 \ \text{参数} \times 2\ \text{B} = 140\ \text{GB} \qquad \frac{140\ \text{GB}}{3.35\ \text{TB/s}} \approx 42\ \text{ms} $$

**所以**：既然你**无论如何都要为读权重付这笔钱**，那就**为 32 个序列一起读，而不是 1 个**。

| 指标 | batch=1 → batch=32 的变化 |
|---|---|
| 搬运的字节数 | **几乎不变** |
| 有效功 | **乘以 32** |
| 算术强度 | **向 ridge 爬升** |

> ⚠️ **这是全书最容易被误解的一句话**：
> **"batching 不会让任何单个用户变快：它让你已经在付的内存流量做更多的工作。"**
>
> 翻成你熟悉的语言：**batching 提升 throughput，不降低 latency**（单请求延迟甚至略增）。

**一句话记忆**：

$$ \text{如果你要花钱读权重，就一次读给 32 个序列用} $$

### 4.8 图像生成在 ridge 的另一侧

| | LLM decode | 图像/视频生成 |
|---|---|---|
| 每步做的事 | 一次小的矩阵-向量乘 | **对完整 latent 的一次大规模并行操作** |
| 算术强度 | 全程低 | **全程高** |
| 瓶颈 | memory bound | **compute bound（从头到尾）** |

**这改变了哪些手段有效**：

| 手段 | 对 LLM decode | 对图像生成 |
|---|---|---|
| **Batching** | 颠覆性的 | **作用小得多**——因为你**已经在打满 tensor core 了** |
| **更低精度** | 有效 | **有效** |
| **更好的 kernel** | 有效 | **有效** |
| **更少的步数** | 不适用 | **有效（这是图像特有的手段）** |

> 💡 这张表是**面试里最容易展现"你会建模"的地方**：同一个手段（batching）在不同瓶颈下效果天差地别，**原因是算术强度在 ridge 的哪一侧**。

## 5. 优化 attention

### 5.1 为什么 attention 是重点

- **对 LLM**：二次复杂度（实践中靠 KV cache 变线性，**但线性算法也很贵**）——"**attention 是跨模型、跨架构最贵的一部分推理**"
- **attention 很敏感**：**"每个 token 依赖每一个先前 token，attention 里的小误差会快速累积，所以 attention 优化是个精细活。"**

### 5.2 基础实现低效在哪

回到上面的三行伪码——**中间矩阵 S 和 P 在一个步骤结束时被存储，紧接着在下一个步骤开始时就立刻被加载**。

$$ \text{S, P 的"存了马上读"} = \text{纯粹的浪费} \quad\Longrightarrow\quad \text{这就是 FlashAttention 要解决的问题} $$

### 5.3 两条优化路线

| 路线 | 特点 | 代表 |
|---|---|---|
| **实现改进** | **无损**（不影响质量），但**仍受二次复杂度限制**。让长序列在今天的硬件上变得可行 | FlashAttention、PagedAttention |
| **新算法** | 用**更好的时间/空间复杂度**换一些质量（训练技巧可以减小影响） | sliding window、gated、linear、compressed、multi-latent |

### 5.4 FlashAttention —— 一个值得记住的对比

作者给了个很有冲击力的数字对比：

| | 代码量 |
|---|---|
| 基础 attention 算法 | **几十行** |
| **FlashAttention** | **几万行** |

**数学操作完全相同**，区别是**为特定 GPU 手工融合 kernel，实现得更省内存访问**。

**要点**：
- 靠**消除多余的内存读写**、并把 attention 算法**精确地排布以贴合 GPU 的能力**
- **FlashAttention for H100 和 for B200 是不同的代码**
- **对 compute-bound 的操作尤其有用**（LLM prefill、视频生成）

### 5.5 PagedAttention

**解决的问题**：KV cache 会迅速变大、填满显存，读起来也费时间。

**做法**：把 KV cache **切成块（page）**，通过**查找表**访问。

**收益**：**KV cache 可以以碎片化的内存跨 GPU 存储，而不需要一整块连续内存。**

### 5.6 改变复杂度的 attention 变体

| 变体 | 做法 |
|---|---|
| **Sliding window** | 只对**前 w 个 token 的滑动窗口**算 attention，把 $O(N^2)$ 变成 $O(Nw)$，**w 常在 8K-32K** |
| **Gated attention** | 训练时引入的层类型，允许**对某些上下文块以线性时间近似** attention |
| **Linear attention** | 用线性时间算法**近似**替代二次的 softmax 公式 |
| **Compressed attention** | 周期性**压缩序列较早的上下文**，attention 同时考虑压缩上下文和未压缩的近期 token |
| **Multi-latent attention** | 在**低维 latent 空间**里近似 attention |

**背后的直觉**（作者讲得很好）：**序列里彼此靠近的 token 互相影响更大**。
> "我现在写的这句话紧接上一句，但和本章开头那句话的关系就没那么紧。"

**关键工程点**：这个直觉**可以通过训练来扩展**——像 sliding window attention **在训练时也应用**，就会得到**在推理时用同样技术仍保持高质量**的模型。

**另一条路：绕开 attention 架构本身**：
- **Mamba**：选择性状态空间模型，**用循环状态更新替代 self-attention，对序列长度实现线性扩展**
- **混合模型**：有时把 Mamba 风格的状态空间块和 transformer 块混用。作者指出**应用还比较有限，但混合模型越来越流行**（如 NVIDIA Nemotron 3 Nano）

## 6. 本章小结与自测

### 关键认知（这一章的"必背清单"）

1. **两个资源：算力 + 带宽。哪个饱和决定什么优化值得做。**
2. $I_{ridge} = \text{Peak FLOPS} / \text{Bandwidth}$；**H100 FP16 ≈ 295 ops/byte**
3. $I < I_{ridge}$ → **memory bound（优化搬运）**；$I > I_{ridge}$ → **compute bound（优化 kernel/降精度）**
4. **prefill 算力受限、decode 带宽受限、图像视频生成算力受限**
5. **decode 算术强度的算例：d=128、N=4096、FP16 → $I \approx 62 \ll 295$**
6. **70B FP16 每 token 搬 140GB，H100 光读 42ms** → **这就是 batching 存在的全部理由**
7. **batching 不降低单用户延迟，只提升吞吐**（"让已付的流量做更多工作"）
8. **图像生成在 ridge 另一侧，batching 几乎没用**（tensor core 已饱和）
9. **激活函数的存在理由是"打断线性"**，否则多层 matmul 会坍缩成一层
10. **FFN 占权重最大，attention 是推理时更复杂的操作**（且 attention 最敏感、最难量化）
11. **attention 基础算法几十行，FlashAttention 几万行**——数学相同，实现不同
12. **KV cache 是全书枢纽**：prefill 建、decode 用、占显存、可复用、要传、需量化
