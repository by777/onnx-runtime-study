# 第一层：直觉

## 0. 一个类比：通读全文 → 做笔记 → 逐字写答案

**场景**：给你一篇文章，要你写一段回答。

人的做法：
1. **通读全文**，边读边把要点记在便签上
2. **看着便签，逐字写答案**——写第一个字时看便签，写第二个字时也看便签……

对应到 LLM：

| 人的动作 | LLM 的动作 | 术语 |
|---|---|---|
| 通读全文 | 把整个 prompt **一次并行**处理 | **Prefill** |
| 便签（记下要点） | 每层的 K/V 存起来 | **KV cache** |
| 逐字写答案 | 每步只生成 1 个 token | **Decode** |
| 写答案时查便签 | 从 KV cache 读历史 | —— |
| **不重读原文** | **不重算** prompt 的 attention | ← 这就是 KV cache 的全部意义 |

**类比里最关键的一环**：写答案时你**不重读原文**，只查便签。如果每写一个字都重读一遍原文，你会崩溃——**LLM 不用 KV cache 就是这个下场**（第 4 节会算出具体倍数）。

**类比不成立的地方**（提前说清，免得推出错误结论）：

| 类比 | 实际 |
|---|---|
| 人"通读"是串行的 | LLM 的 prefill 是**完全并行**的（64 个 token 同时算） |
| 便签是简化记录 | KV cache 是**精确的**，不丢信息 |
| 便签写在纸上，容量固定 | KV cache 随上下文**线性增长**（这反而是问题） |

## 1. 根本原因：输出必须串行，输入可以并行

这一节回答"**为什么**要分两段"。如果跳过这节，后面全是死记硬背。

### 1.1 自回归：输出的串行性

LLM 建模的是一个概率分解：

$$ P(x_1, x_2, \ldots, x_T) \;=\; \prod_{t=1}^{T} P\!\left(x_t \mid x_1, \ldots, x_{t-1}\right) $$

第 $t$ 个 token 依赖前 $t-1$ 个。**这是因果依赖，绕不过去。**

要生成第 5 个 token，必须**先知道**第 4 个是什么。而第 4 个是采样出来的（即使 temperature=0 用 argmax，也得先把它算出来）。

$$ \boxed{\text{输出天然串行：第 } t \text{ 步必须等第 } t-1 \text{ 步算完}} $$

### 1.2 输入的并行性从哪来

prompt 是用户给的——**所有 token 一开始就都在手上**，没有"必须先知道前一个"的问题。

再叠加 Transformer 的结构性质：**causal mask 让每个位置只看它前面**：

```
位置 1  只看 [1]
位置 2  只看 [1,2]
位置 3  只看 [1,2,3]
...
位置 64 只看 [1..64]
```

**位置 3 的计算不需要等位置 4**——它们之间没有互相依赖。所以这 64 个位置可以**一次矩阵乘法全算完**。

$$ \boxed{\text{输入：64 个位置互相独立} \;\Rightarrow\; \text{一次算完（矩阵乘）}} $$

### 1.3 于是产生了两段

$$ \text{一次请求} \;=\; \underbrace{\text{并行处理输入}}_{\text{Prefill，跑 } 1 \text{ 次}} \;+\; \underbrace{\text{串行生成输出}}_{\text{Decode，跑 } N_{out}-1 \text{ 次}} $$

### 1.4 ⚠️ 一个必须纠正的误解

**很多人（包括我第一遍）以为**：分两段是因为"输入必须并行、输出只能串行"。

**更准确的说法**：

$$ \text{分两段的根本原因是「\textbf{输出必须串行}」，而不是「输入必须并行」} $$

为什么这个区别重要：

- 输入其实**也可以**一个 token 一个 token 地喂（有实现真这么调试）——**这在功能上完全正确**
- 只是那样会**浪费复用率**：同一个权重被搬进来 $N$ 次、每次只用 1 次（第 6 节定量）
- 所以 prefill 的本质是：

$$ \boxed{\text{Prefill = 把 } N \text{ 次本该串行的前向，合并成 } 1 \text{ 次}} $$

**它是一个"合批"操作**——把 $N$ 个独立的前向合成一个大矩阵乘。这才是它快的真实原因，不是"因为输入并行"。

> 💡 **联系你的 T41 经验**：这就是**批处理提高 MAC 利用率**。一次 NNMAC 喂 1 个数据 vs 喂满一条流水线，硬件利用率天差地别。prefill 干的就是"把流水线喂满"这件事。

# 第二层：机制

## 2. 数字设定（后面所有计算都用它）

为了让数字可复算，先固定一个**简化模型**：

| 参数 | 值 | 说明 |
|---|---|---|
| 参数量 $P$ | 7B | 中等规模，常见 |
| 层数 $L$ | 32 | |
| 隐藏维度 $d$ | 4096 | |
| KV head 数 | 8（GQA） | 每 4 个 Q head 共享 1 组 KV |
| head_dim | 128 | |
| 精度 | FP16（2 bytes） | |
| 硬件 | H100 | 989 TFLOPS / 3.35 TB/s → **ridge 295 ops/byte** |
| 输入 | 64 token | |
| 输出 | 32 token | |

**权重总大小**：

$$ 7 \times 10^9 \times 2 \text{ B} = 14 \text{ GB} = 13.04 \text{ GiB} $$

**在 H100 上光读一遍权重的耗时**：

$$ \frac{14 \times 10^9}{3.35 \times 10^{12}} \approx 4.18 \text{ ms} $$

> ⚠️ **记住这个 4.18 ms**，后面全靠它算账。

## 3. Prefill 慢放：它到底在算什么

### 3.1 输入形状

prompt 先 tokenize，然后查 embedding 表：

$$ \text{64 个 token id} \;\longrightarrow\; X_{64 \times 4096} $$

**注意形状**：$64 \times 4096$——**第一维是 64（token 数），不是 1**。

### 3.2 逐层展开（拿第 1 层举例）

| 步骤 | 运算 | 形状变化 |
|---|---|---|
| ① QKV 投影 | $X \cdot W_Q$、$X \cdot W_K$、$X \cdot W_V$ | $[64,4096] \to [64,4096]$ |
| ② 注意力分数 | $Q K^\top$ | $[64,4096] \to [64,64]$（8 个 head 各 $64\times64$） |
| ② softmax + mask | 逐元素 | $[64,64] \to [64,64]$ |
| ② 加权求和 | $P V$ | $[64,64] \to [64,4096]$ |
| ③ 输出投影 | $\cdot W_O$ | $[64,4096] \to [64,4096]$ |
| ④ FFN | 两个线性层 | $[64,4096] \to [64,16384] \to [64,4096]$ |

**每个矩阵的第一维都是 64**——这就是"并行处理 64 个 token"的具体含义。

### 3.3 ⚠️ 一个反直觉的事实：算出的 64 行里，只有 1 行有用

这是很多人没注意到、但很有价值的一点。

prefill 前向跑完，输出是 $Y_{64 \times 4096}$（还没到 logits），然后：

- **最后一行的 hidden state** → 送进输出层 → 得到 logits → **采样出第 1 个输出 token**
- **前 63 行的 hidden state** → **不送去算 logits**（我们不需要"第 3 个位置的预测"，那是在补全 prompt，不是我们要的）

**那前 63 行白算了？不是。** 它们有两个用处：

| 用处 | 说明 |
|---|---|
| **① 生成了 KV cache** | 每层的 K、V 都从这些行算出来并**存下来**，decode 阶段要用 |
| **② 构成了因果上下文** | 位置 64 的 attention 需要看位置 1..63 的 K/V |

所以准确的说法是：

$$ \boxed{\text{Prefill 的计算量 ≈ } N \text{ 倍于单 token，但产出的「有效输出」只有 } 1 \text{ 个 token}} $$

**这才是 prefill "贵"的真正原因**——它做了 64 倍的活，只换来 1 个 token。

**那为什么还值得？** 因为如果不用 prefill（一个一个喂），这 64 次前向**每次都要把 13 GiB 权重重读一遍**：

$$ 64 \text{ 次} \times 4.18 \text{ ms} = 268 \text{ ms} \qquad\text{vs}\qquad \text{prefill 一次} \approx 4.2 \text{ ms} $$

**64 倍差距。** 这就是第 1.4 节说的"合批"的价值。

### 3.4 Prefill 的时间去哪了

用 4.18 ms 的权重读取时间做基准：

$$ \text{计算量} = 2 \times P \times N = 2 \times 7\times 10^9 \times 64 \approx 896 \text{ GFLOP} $$

$$ \text{纯计算耗时} = \frac{896 \times 10^9}{989 \times 10^{12}} \approx 0.91 \text{ ms} \qquad \text{访存耗时} \approx 4.18 \text{ ms} $$

算术强度：

$$ I = \frac{2PN}{2P} = N = 64 \quad (\text{精确算：} 63.9) $$

$$ 64 \;<\; 295 \quad\Longrightarrow\quad \textbf{64 token 的 prefill 其实还是带宽受限的！} $$

**这有点反直觉**——"prefill 不是算力受限吗？"

**答案**：**要序列够长才是**。临界点在 $N \approx 295$ 附近（第 7 节会揭晓这个数为什么正好是 295）。

| 输入长度 | $I$ | 判定 |
|---|---|---|
| 64 token | 63.9 | 带宽受限 |
| 256 token | 254.2 | 带宽受限 |
| **297 token** | ~295 | **平衡点** |
| 1024 token | 1004.7 | 算力受限 |
| 4096 token | 3804.2 | 算力受限 |

**所以"prefill 算力受限"这句话的完整版是**：

> **足够长的 prefill（输入 > ~300 token）算力受限；很短的 prefill 仍可能带宽受限。**

实际服务里输入动辄几百上千 token，所以"prefill 算力受限"作为经验法则是对的——**但要知道它的适用边界**。

## 4. Decode 慢放：它到底在算什么（以及为什么必须有 KV cache）

### 4.1 先看没有 KV cache 会发生什么

**朴素做法**：第 $t$ 步要生成第 $t+1$ 个 token，就把**目前全部** $t$ 个 token 喂进去算一遍。

| 第几步 | 喂入 token 数 | attention 计算量（每层） |
|---|---|---|
| 1 | $N$ | $O(N^2 d)$ |
| 2 | $N+1$ | $O((N+1)^2 d)$ |
| $\vdots$ | | |
| 末 | $N+M$ | $O((N+M)^2 d)$ |

**总计算量**（设总长度 $N$）：

$$ \sum_{t=1}^{N} t^2 d \;\approx\; \frac{N^3 d}{3} $$

**有 KV cache 时**：每步只喂 1 个新 token，attention 只需 $Q[1,d] \times K^\top[d,t]$：

$$ \sum_{t=1}^{N} t \cdot d \;=\; \frac{N^2 d}{2} $$

**加速比**：

$$ \frac{N^3 d / 3}{N^2 d / 2} = \frac{2N}{3} \;\xrightarrow{\;N=4096\;}\; \mathbf{2731 \text{ 倍}} $$

线性层那部分同理：

$$ \text{无 cache：} \sum_{t=1}^{N} t d^2 \approx \frac{N^2 d^2}{2} \qquad \text{有 cache：} N d^2 \qquad \Rightarrow \quad \frac{N}{2} = 2048 \text{ 倍} $$

$$ \boxed{\text{KV cache 把 decode 的复杂度从 } O(N^2) \text{ 降到 } O(N)} $$

> 💡 **所以 KV cache 的第一目的不是"省显存"——是省计算。**
> 显存是它的**代价**（而且这个代价后来变成了大问题，见 07 章的 KV cache 分级存储）。

### 4.2 有 KV cache 后的 decode

**第 $t$ 步的输入**：

$$ \text{只有 1 个 token} \;\longrightarrow\; x_{1 \times 4096} $$

**注意形状**：$1 \times 4096$——**第一维是 1**。这就是和 prefill 唯一的形状差别。

逐层展开：

| 步骤 | 运算 | 形状 | 和 prefill 的区别 |
|---|---|---|---|
| ① QKV 投影 | $x \cdot W_Q$ 等 | $[1,4096] \to [1,4096]$ | **矩阵乘退化成向量-矩阵乘** |
| ① 追加 KV | 把新的 K、V 接到 cache 尾部 | cache 长度 $t-1 \to t$ | 只有 prefill 有 |
| ② 注意力分数 | $Q K^\top_{\text{cache}}$ | $[1,4096] \to [1, t]$ | $t$ 是**历史总长**，不是 1 |
| ② softmax | 逐元素 | $[1,t]$ | 只看第 1 行 |
| ② 加权求和 | $P V_{\text{cache}}$ | $[1,t] \to [1,4096]$ | |
| ③ 输出投影 | $\cdot W_O$ | $[1,4096] \to [1,4096]$ | |
| ④ FFN | 两个线性层 | $[1,4096] \to [1,16384] \to [1,4096]$ | |

### 4.3 ⚠️ 看清楚这里发生了什么

**每一个权重矩阵都要完整读一遍**（$W_Q, W_K, W_V, W_O$、FFN 的两个——整整 13.04 GiB），

**但每个只用了一次**——乘一个 $1 \times 4096$ 的行向量。

$$ \boxed{\text{搬进来 13 GiB，做了 } 2 \times 7\text{B} = 14 \text{ GFLOP} \;\Rightarrow\; I = 1.0} $$

$$ 1.0 \;\lll\; 295 \quad\Longrightarrow\quad \textbf{极端带宽受限} $$

**换算成时间**：

$$ \text{每 token 耗时} \ge \frac{14 \text{ GB}}{3.35 \text{ TB/s}} = 4.18 \text{ ms} $$

$$ \text{单用户上限} = \frac{1}{4.18 \text{ ms}} \approx \mathbf{239 \text{ token/s}} $$

**70B 模型**：权重 140 GB →

$$ \frac{140}{3.35} \approx 41.8 \text{ ms/token} \;\Rightarrow\; \mathbf{24 \text{ token/s}} $$

**这就是"大模型吐字慢"的物理极限**——和你的算力、优化技巧**全都无关**，纯粹是"必须把 140 GB 搬一遍"。

> 🔬 `python3 prefill_vs_decode.py --trace` 会把 7B 模型一次请求的账算给你看：
> **权重被读 32 次，光读权重就 134 ms。**

## 5. 一个关键澄清：同一套权重、同一个函数

### 5.1 阶段 vs 模块（两个不同的轴）

这是 03 章 2.3.1 讲过的，但值得再看一遍——**因为它是最容易混的地方**：

| | **阶段（时间维度）** | **模块（结构维度）** |
|---|---|---|
| 术语 | **Prefill / Decode** | **Encoder / Decoder** |
| 回答什么 | 一次请求**内部的时间结构** | 模型**由什么部件构成** |
| 类比 | 做菜的**先后步骤** | 厨房里的**设备** |

$$ \text{decode（解码阶段）} \;\ne\; \text{decoder（解码器，一个模块）} $$

### 5.2 实现层面的真相：它们就是同一个函数

**这是最有力的澄清**。伪代码：

```python
def forward(tokens, kv_cache):
    # tokens: [N, d]
    #   prefill 时 N = 输入长度（如 64）
    #   decode  时 N = 1
    for layer in model.layers:
        q = tokens @ layer.W_q          # [N, d]  ← 同一个矩阵乘
        k = tokens @ layer.W_k
        v = tokens @ layer.W_v

        k, v = kv_cache.append_and_get(layer, k, v)   # decode 时读历史
        out = attention(q, k, v)                       # ← 同一段代码
        tokens = out @ layer.W_o
        tokens = ffn(tokens)
    return tokens
```

**看清楚：**

| | Prefill | Decode |
|---|---|---|
| 调用的函数 | `forward` | `forward` ← **一模一样** |
| 权重 | 同一份 | 同一份 ← **一模一样** |
| 代码路径 | 同一条 | 同一条 ← **一模一样** |
| **唯一差别** | `N = 64` | `N = 1` |

$$ \boxed{\text{Prefill 和 Decode 不是两段代码，是两个【不同的张量形状】}} $$

**一个实现细节上的补充**：decode 时 KV cache 要"追加 + 读全部"，所以多一个 IO 操作；但这不是"两套算法"，只是多一行 `append`。

### 5.3 那为什么要给它们起两个名字？

因为**工程上要区别对待**：

| 原因 | 说明 |
|---|---|
| **瓶颈不同** | 一个算力受限、一个带宽受限 → **优化手段完全不同**（见 9 节） |
| **指标不同** | prefill 决定 TTFT（首字延迟），decode 决定 TPOT（吐字速度） |
| **部署可能不同** | 可以拆到**不同的硬件**上跑（PD 分离，见 9.4） |
| **代码分支不同** | 实际引擎里确实有 `if is_prefill:` 的分支——但**是为了 kernel 选择**（如 FlashAttention 的两种 kernel、chunked prefill 的调度），**不是为了用不同的权重** |

> ⚠️ **区分"工程上分开处理"和"模型上是两个东西"**。前者是真的，后者是假的。

### 5.4 encoder-decoder 模型（如 Whisper）的对应关系

这里有真的 encoder 和 decoder 了，但**映射不是一一对应的**：

```
Whisper = encoder + decoder

  encoder：处理 30 秒音频（log-Mel 频谱）→ 音频特征      ← 只跑【1 次】
                                                          形状上类似 prefill（整段输入并行）
  decoder：自回归生成文本 token                           ← 跑【很多次】
              └─ 它内部【本身又分】prefill 和 decode
```

| 部件 | 跑几次 | 内部有没有 prefill/decode 之分 |
|---|---|---|
| LLM 的 decoder 栈 | prefill 1 次 + decode $N_{out}-1$ 次 | ✅ **就是它** |
| Whisper 的 **encoder** | **1 次** | ❌ **没有**（只跑一次，不涉及逐 token） |
| Whisper 的 **decoder** | 很多次 | ✅ **它内部再分 prefill 和 decode** |

**关键**：**encoder 那部分没有 prefill/decode 的划分**——它只跑一次，不是自回归的。

> 💡 这也解释了 08 章说的"Whisper 的时间绝大部分花在 decoder 上"：encoder 只跑 1 次，decoder 要自回归很多次。

# 第三层：定量

## 6. 复用率：一切结论的源头

### 6.1 用一个线性层算透（先忘掉 attention）

$y = Wx$，其中 $W$ 是 $4096 \times 4096$，FP16 → **这一份权重就是 32 MiB**。

| | **Decode（1 token）** | **Prefill（1024 token）** | 变化 |
|---|---|---|---|
| 搬入权重 $W$ | **32.0 MiB** | **32.0 MiB** | **完全一样** ← |
| 搬入输入 | 8.0 KiB | 8.0 MiB | ×1024 |
| 写出结果 | 8.0 KiB | 8.0 MiB | ×1024 |
| **总访存** | **32.02 MiB** | **48.00 MiB** | **×1.5** |
| **总运算量** | **33.55 MFLOP** | **34.36 GFLOP** | **×1024** |
| **算术强度 $I$** | **1.00** | **682.67** | **×683** |
| vs H100 平衡点 295 | **带宽受限** ❌ | **算力受限** ✅ | |

### 6.2 请盯着这两行

$$ \text{访存：} 32.02 \to 48.00 \text{ MiB} \quad (\times 1.5) $$

$$ \text{运算：} 33.55 \text{ M} \to 34.36 \text{ G} \quad (\times 1024) $$

$$ \boxed{\text{权重那一份【完全没变】，只是被 1024 个 token 复用了}} $$

**分子涨 1024 倍、分母几乎不动** ⇒ $I$ 从 1.00 涨到 682.67，一步跨过 295。

$$ \boxed{\text{prefill 和 decode 的全部差别，就是这一件事}} $$

### 6.3 一般化：算术强度随复用率怎么变

固定 $W$（$4096\times4096$），让 token 数 $N$ 从 1 涨到 1024：

| token 数 $N$ | 总访存 | 总运算 | $I$ | 判定 |
|---|---|---|---|---|
| **1**（decode） | 32.02 MiB | 33.55 MFLOP | **1.00** | 带宽受限 |
| 2 | 32.03 MiB | 67.11 MFLOP | 2.00 | 带宽受限 |
| 8 | 32.12 MiB | 268.44 MFLOP | 7.97 | 带宽受限 |
| 32 | 32.50 MiB | 1.07 GFLOP | 31.51 | 带宽受限 |
| 128 | 34.00 MiB | 4.29 GFLOP | 120.47 | 带宽受限 |
| **344.6** | **37.39 MiB** | **11.56 GFLOP** | **295.00** | **← 平衡点** |
| 1024 | 48.00 MiB | 34.36 GFLOP | 682.67 | 算力受限 |

> 📌 **数字口径**：以上与 `prefill_vs_decode.py --reuse` 的输出**逐位一致**（含激活流量）。
> 平衡点是解 $I(N) = 295$ 得到的 $N = 344.6$。

$$ \boxed{\text{复用率} = \frac{\text{一份数据搬进来，参与了多少次运算}}{\text{}} = \text{token 数 } N} $$

**⚠️ 注意区分两个"平衡点"**（后面的 7.2 节会给出另一个数，这不是矛盾）：

| 口径 | 公式 | 平衡点 $N$ |
|---|---|---|
| **单个线性层**（本节） | $I = \dfrac{i o N}{i o + (i+o)N}$ | **344.6** |
| **整个 7B 模型**（7.2 节） | $I = \dfrac{2PN}{2P + 2NLd}$ | **296.6** |

**为什么不同**：单层公式里"每 token 的激活流量"是 $2(i+o)N$（只这一层的输入输出）；
整模型里是 $2NLd$（所有层的激活，$L=32$ 摊下来**每层更小**）。

$$ \text{两者形式相同，只是"每 token 的额外流量"这一项的口径不同} \;\Longrightarrow\; \text{平衡点相差约 } 16\% $$

**所以"约 300 个 token"是个好记的近似；要精确值必须说清是哪个口径。**

### 6.4 ⚠️ 但算术强度不是无限涨的：渐近上限

$$\frac{2 \cdot i \cdot o \cdot N}{2 \cdot (i \cdot o + i \cdot N + o \cdot N)} \;=\; \frac{i \cdot o \cdot N}{i \cdot o + (i+o)N}$$

当 $N \to \infty$：

$$ I_\infty \;=\; \frac{i \cdot o}{i + o} \qquad (i = \text{输入维度},\ o = \text{输出维度}) $$

| 形状 $i \times o$ | $I_\infty$ | 判定（vs 295） |
|---|---|---|
| $4096 \times 4096$ | **2048** | 算力受限 |
| $4096 \times 1024$ | 819 | 算力受限 |
| $4096 \times 256$ | **240.9** | **★ 永远带宽受限** |
| $8192 \times 8192$ | 4096 | 算力受限 |

**这条结论原书没讲，但很实用**：

> **瘦长层（做降维的层，如 down-projection、MoE 的专家层），即使 prefill 也可能永远带宽受限。**

因为 $i \to \infty, o$ 很小时 $I_\infty \to o$。比如 $o = 128$ 的降维层，$I_\infty \approx 128 < 295$——**无论序列多长都翻不过去**。

**这解释了为什么 MoE 模型的 prefill 优化很难做**：MoE 层是一堆瘦长的小矩阵，天生低算术强度。

### 6.5 对着 T41 经验看

| 你做过的事 | 本质 |
|---|---|
| **「切 NNMAC 能吃的块」+ 索引复用** | **提高复用率** ⇒ 提高 $I$ |
| **「DMA full」** | **带宽触顶** ⇒ 落在 $I < I_{ridge}$ 那一侧 |
| **pingpong 双缓冲** | 搬运/计算重叠，**掩盖访存**（不改 $I$，改的是"等多久"） |
| **WRAM/FRAM 片上存储** | 让数据**不用出片** ⇒ 减少分母 |

$$ \boxed{\text{Roofline 不是新知识，是给你已经在做的事配了一套坐标系}} $$

**prefill / decode 就是这套坐标系在 LLM 上的一个应用实例。**

## 7. 一个漂亮的定量结论：LLM 的算术强度 ≈ token 数

### 7.1 推导

**忽略激活流量**（后面会验证这个忽略是否合理），把整个模型看成一个整体：

| 量 | 表达式 | 说明 |
|---|---|---|
| 权重访存 | $2P$ bytes | FP16 下每个参数 2 字节 |
| 每 token 运算 | $2P$ FLOPs | 每个参数 2 FLOP（乘 + 加） |
| 处理 $N$ 个 token 的总运算 | $2PN$ FLOPs | |
| 算术强度 | $\dfrac{2PN}{2P}$ | |

$$ \boxed{\;I \;\approx\; N \quad \text{（token 数）}\;} $$

**为什么这么简洁**：FP16 下**每个参数 2 字节、每 token 每参数 2 FLOP**——**两个 2 正好抵消**。

（如果用 FP8：每参数 1 字节、2 FLOP → $I = 2N$。用 INT4：1 字节/2 个参数 → $I = 4N$。**这个推论很重要，见 7.3**。）

### 7.2 于是平衡点就是"约 300 个 token"

H100 的 ridge 是 295 ops/byte，而 $I \approx N$，所以：

$$ N \approx 295 \;\Longrightarrow\; \text{从这里开始，算力成为瓶颈} $$

**验算**（含激活流量，$L = 32,\ d = 4096$）：

$$ I = \frac{2PN}{2P + 2NLd} = \frac{7\times10^9 \, N}{7\times10^9 + 131072\,N} $$

| $N$ | 精确 $I$ | 近似 $N$ | 判定 |
|---|---|---|---|
| 1 | **1.0** | 1 | 带宽受限（decode） |
| 64 | **63.9** | 64 | 带宽受限 |
| 256 | 254.2 | 256 | 带宽受限 |
| **297** | **~295** | 295 | **平衡点** |
| 1024 | **1004.7** | 1024 | 算力受限（prefill） |
| 4096 | 3804.2 | 4096 | 算力受限 |
| $\infty$ | $\to \dfrac{P}{Ld} = 53406$ | — | 上限 |

**近似 $I \approx N$ 在 $N \lesssim 1000$ 时误差 < 3%**（因为激活流量相对权重还很小）。$N$ 很大时误差变大（向 $P/(Ld)$ 收敛），但**判定方向不会错**。

> ⚠️ **别把"295 ops/byte"和"295 个 token"混为一谈**。它们是**不同的量**（一个硬件一次性能做多少 op/byte，一个算法每 byte 能做多少 op）——只是**在 FP16 LLM 这个特殊场景下数值恰好相等**。这是巧合，不是恒等式。

### 7.3 量化的另一面：它把"那道坎"降低了

用 7.1 的推导看量化对 $I$ 的影响：

| 精度 | 权重字节/参数 | FLOP/参数 | $I$ | 需要多少 token 才平衡 |
|---|---|---|---|---|
| FP16 | 2 | 2 | $N$ | 295 |
| **FP8** | 1 | 2 | $2N$ | **148** |
| **INT4** | 0.5 | 2 | $4N$ | **74** |

$$ \boxed{\text{量化 = 把 ridge 那道坎从「295 个 token」降到「74 个 token」}} $$

**这就是量化对 decode 收益巨大的根本原因**：

- decode 时 $N = 1$（或 batch 后 = batch size），**离平衡点还差得远** → 稳稳带宽受限
- 量化把权重从 2 字节压到 1 字节或 0.5 字节 → **分母直接减半或减到 1/4**
- 于是**吐字速度可以接近翻倍/翻 4 倍**（如果纯权重主导）

**注意**：这不是"量化让 decode 变成算力受限"——$I = 4N$ 在 $N=1$ 时也只有 4，还是带宽受限。**它只是让分母变小了。**

> 💡 对照 [06 量化](06_量化_动态范围与粒度.md)：那里讲"动态范围 vs 粒度"是**精度**视角；这里是**性能**视角。两个视角要能各自独立说清。

### 7.4 batching 的定量收益

既然 $I \approx N$，而 batching 就是把 $N$ 从 1 变成 batch size：

| batch size | $I$ | 相对单请求 | 判定 |
|---|---|---|---|
| 1 | 1.0 | 1× | 带宽受限 |
| 8 | 8.0 | 8× | 带宽受限 |
| 32 | 32.0 | 32× | 带宽受限 |
| 128 | 128.0 | 128× | 带宽受限 |
| **~300** | **~295** | **~295×** | **平衡点** |

$$ \boxed{\text{batching 的全部原理 = 提高复用率 = 把 } I \text{ 从 } 1 \text{ 往上推}} $$

**为什么实际 batch 很少开到 300**：

| 约束 | 说明 |
|---|---|
| **KV cache 容量** | batch 越大 KV cache 越大（第 8 节），显存不够 |
| **延迟** | batch 越大，单个请求的排队时间越长 |
| **收益递减** | 接近平衡点后继续加 batch 收益趋缓 |

实际服务常用 batch 几十到一两百——**在"利用率"和"延迟/显存"之间取平衡**。

## 8. Decode 访存的另一块：KV cache

前面把 decode 的访存说成"就是权重"，这一节补上被忽略的另一半。

### 8.1 KV cache 有多大

每 token 的 KV cache 大小：

$$ \underbrace{2}_{K \text{ 和 } V} \times L \times n_{kv} \times d_{head} \times \underbrace{2 \text{ B}}_{\text{FP16}} $$

| 模型 | 每 token KV | 权重 | **交叉点**（KV 总量 = 权重） |
|---|---|---|---|
| **7B**（GQA 8） | **128 KiB** | 13.04 GiB | **≈ 106,800 token** |
| **70B**（GQA 8） | **320 KiB** | 130.39 GiB | **≈ 427,000 token** |

### 8.2 这个交叉点意味着什么

$$ \boxed{\text{在常规上下文长度（几千到几万 token）下，decode 的访存【几乎全是权重】}} $$

- 4096 token 的 KV cache 只有 $4096 \times 128 \text{ KiB} = 512 \text{ MiB}$，相对 13.04 GiB 权重是 **3.8%**
- 要到**十万 token 量级**，KV cache 才和权重等量

**这解释了两件事**：

| 现象 | 解释 |
|---|---|
| "decode 带宽受限"为什么主要归咎于权重 | 常规长度下 KV 占比 <5% |
| 为什么**长上下文**是另一类问题 | 十万 token 时 KV cache 开始主导，**解码速度随上下文长度明显下降** |

> 💡 **"长上下文"的定义**：07 章引了原书一句很妙的话——*"当一个序列生成的 KV cache 大到足以在推理中造成问题，它就成了长上下文"*。**这个"大到造成问题"的临界点，就是这张表的交叉点。**

### 8.3 加上 KV 后的完整访存公式

$$ \text{每步 decode 访存} \;=\; \underbrace{2P}_{\text{权重，固定}} \;+\; \underbrace{2 \cdot L \cdot n_{kv} \cdot d_{head} \cdot 2 \cdot N}_{\text{KV cache，随 } N \text{ 线性}} $$

**这是两条线的和**：

```
访存
  ↑
  │                    ╱  ← KV cache（随 N 线性增长）
  │                  ╱
  │                ╱
  │──────────────●────────────  ← 权重（恒定 13.04 GiB）
  │            ╱ ↑
  │          ╱  交叉点（~10 万 token）
  │        ╱
  └──────────────────────────→ 上下文长度 N
```

**这是一个很有用的心智模型**：decode 的成本 = **常数项（权重）+ 增长项（KV）**。
- 短上下文：常数项主导 → **优化权重（量化！）收益最大**
- 长上下文：增长项主导 → **优化 KV（量化 KV / 卸载 / 稀疏注意力）收益最大**

> 💡 对应 07 章的手段：**KV cache 量化**、**KV cache 分级存储**、**PagedAttention**（减少碎片）、**KV-aware 路由**——全都作用在这个"增长项"上。

# 第四层：工程

## 9. 这个区分在工程上导致什么后果

### 9.1 度量指标：两个阶段各管一个指标

| 指标 | 全称 | 由谁决定 | 用户的感受 |
|---|---|---|---|
| **TTFT** | Time To First Token | **Prefill** | "它在想"的时间 |
| **TPOT / ITL** | Time Per Output Token / Inter-Token Latency | **Decode** | "它吐字快不快" |

$$ \boxed{\text{TTFT} \leftrightarrow \text{prefill} \leftrightarrow \text{算力受限}} \qquad \boxed{\text{TPOT} \leftrightarrow \text{decode} \leftrightarrow \text{带宽受限}} $$

**这个对应关系非常有用**——它让你能"看指标猜瓶颈"：

| 症状 | 诊断 | 该干什么 |
|---|---|---|
| TTFT 高、吐字快 | **prefill 慢** | 优化 kernel、降低输入长度、prefix cache |
| TTFT 低、吐字慢 | **decode 慢** | **量化、加 batch**、投机解码 |
| 两个都高 | 排队/资源不足 | 加副本、扩容 |

### 9.2 优化手段分两类（别用错）

| 手段 | 作用于 prefill | 作用于 decode | 原理 |
|---|---|---|---|
| **降低权重精度**（量化） | ✅（提升算力） | ✅✅ **主力** | 分母减半/减到 1/4 |
| **不同 kernel**（FlashAttention） | ✅ **主力** | 一般 | 减少中间矩阵搬运 |
| **prefix caching** | ✅✅ **主力** | ❌ | **直接跳过**部分 prefill |
| **投机解码** | ❌ | ✅✅ **主力** | 一次前向多出几个 token（复用率提升） |
| **batching** | 已经是大矩阵 | ✅✅ **主力** | 复用率 1 → batch |
| **KV cache 量化** | ❌ | ✅ | 减少第 8 节的"增长项" |

$$ \boxed{\text{改错阶段 = 白干。先看指标定位阶段，再选手段}} $$

> ⚠️ **必须记住的例子**：**投机解码不改善 TTFT**。因为 TTFT 由 prefill 决定，而投机作用在 decode 阶段。**它是"吐字快"的手段，不是"首字快"的手段。**（这是 07 章强调过的"两阶段纪律"。）

### 9.3 Chunked prefill：让两个阶段混跑

**问题**：一个超长输入的 prefill 会**独占 GPU 很久**（几秒），期间所有正在 decode 的请求都被卡住。

**解法**：**把 prefill 切成小块，和 decode 混在一个 batch 里跑**。

```
不用 chunked：  [=====长 prefill=====][decode][decode][decode]
                                     ↑ 这期间所有请求干等

用 chunked：    [pf块][pf块+decode][pf块+decode][pf块+decode]
                         ↑ 每个 batch 里既有 prefill 又有 decode
```

**为什么有效（用第 7 节的语言）**：

$$ \text{把长 prefill 切块后，它和 decode 拼在一个 batch 里} \;\Longrightarrow\; \text{总 } N \text{ 变大} \;\Longrightarrow\; I \text{ 提高} $$

**它的本质是"批量混合调度"**——不是改算法，是改**怎么组 batch**。

**代价**：实现复杂（调度器要会切、要保证 causal mask 正确、要管多段 KV 的拼接）。

### 9.4 PD 分离（Prefill-Decode Disaggregation）

**观察**：既然两个阶段的瓶颈完全不同，**为什么要在同一块 GPU 上挤？**

| | Prefill 想要的硬件 | Decode 想要的硬件 |
|---|---|---|
| 瓶颈资源 | **算力（FLOPS）** | **带宽（bytes/s）** |
| 理想芯片 | 高算力、大互联 | 大带宽、大显存 |
| 并行策略 | 较小的 TP 就够 | 通常需要更大的 TP（因为权重得装下） |
| batch 形态 | 少量、大 | 大量、小 |

**PD 分离的做法**：起两组 GPU，**prefill 组只做 prefill，decode 组只做 decode**，中间通过 KV cache 传输衔接（prefill 组算完把 KV 传给 decode 组）。

```
用户请求 → [Prefill 池] --KV cache--> [Decode 池] → 流式返回
```

**收益**：两池各自用最适合的配置和 batch 策略，互不干扰。
**代价**：KV cache 要跨节点传输（所以需要高速互联）、调度复杂、需要规模才划算。

> ⚠️ 07 章给的适用范围：**"PD 分离只在你有大量 GPU（常常是多节点）服务同一个模型时才有意义。"** 小规模别碰。

### 9.5 芯片级后果：厂商开始做两块芯片

NVIDIA Rubin 代际的 **CPX 是一块专做 prefill 的独立芯片**。

**这说明什么**：

$$ \boxed{\text{prefill/decode 的差异大到值得用两种芯片分别优化}} $$

这与 PD 分离是同一个逻辑的硬件版：**既然瓶颈不同、最优配置不同，那就各做一块专门的。**

> 💡 **对你的意义（AI 芯片工具链视角）**：这是一个**架构级信号**——推理的"两阶段异质性"已经从软件调度问题上升到了芯片设计问题。你在 T41 上做的"针对特定算子形状优化"，未来可能变成"针对特定阶段优化"。

### 9.6 一张总表

| 维度 | Prefill | Decode |
|---|---|---|
| 一次处理几个 token | $N$（整个输入） | **1** |
| 形状 | $N \times d$ | $1 \times d$ |
| KV cache | **写入** | **读取 + 追加** |
| 跑几次 | **1 次** | $N_{out}-1$ 次 |
| 算术强度 | $\approx N$（通常 > 295） | $\approx 1$ |
| 瓶颈 | **算力**（长输入时） | **带宽**（几乎总是） |
| 决定 | **TTFT** | **TPOT / 吞吐** |
| 主导访存 | 权重（读 1 次） | **权重（每 token 读 1 次）** |
| 主要优化 | FlashAttention、chunked、prefix cache | **量化、batching、投机解码** |
| 与之对应的硬件 | CPX（专做 prefill） | 大显存 + 大带宽的卡 |

# 第五层：排雷

## 10. 六个常见误区

### ❌ 误区 1：prefill 和 decode 是两个模型

**事实**：**同一套权重、同一个 `forward` 函数**，只是 $N$ 不同。见 5.2 的伪代码。

**为什么有人这么想**：因为工程上确实有 `if is_prefill:` 的分支——但那是为了**选 kernel**、**切调度**，不是为了换权重。

### ❌ 误区 2：decoder 就是 decode

**事实**：**两个不同的轴**。

| | decoder | decode |
|---|---|---|
| 是什么 | **模块**（名词） | **阶段**（动词性） |
| 对应 | encoder | prefill |

**LLM 只有一个 decoder 栈，它先干 prefill、再反复干 decode。**

### ❌ 误区 3：decode 比 prefill 慢（或者反过来）

**事实**：要分清「**单步延迟**」和「**每 token 成本**」，而且**prefill 是否算力受限会改变结论**。

**关键：比较时必须用同一个口径。** 分两种情况看：

**情况 A：64 token 的 prefill（带宽受限，$I = 63.9$）**

| | 处理时间 | 处理 token | 每 token 时间 |
|---|---|---|---|
| Prefill（64 token） | **4.18 ms**（读一遍权重，带宽受限） | 64 | **0.065 ms** |
| Decode（1 token） | **4.18 ms**（读一遍权重，带宽受限） | 1 | **4.18 ms** |

**两者总耗时完全相同（都是"读一遍权重"的时间）**——差别只在服务了几个 token：

$$ \frac{4.18}{0.065} = 64 = \text{复用率} \quad\Longrightarrow\quad \boxed{\text{每 token 时间之比} \;=\; \text{复用率之比}} $$

**情况 B：4096 token 的 prefill（算力受限，$I = 3804$）**

| | 处理时间 | 处理 token | 每 token 时间 |
|---|---|---|---|
| Prefill（4096 token） | **58 ms**（算力受限：57.3 TFLOP ÷ 989 TFLOPS） | 4096 | **0.0142 ms** |
| Decode（1 token） | **4.18 ms**（带宽受限） | 1 | **4.18 ms** |

$$ \frac{4.18}{0.0142} \approx 294 \;\approx\; \text{H100 的 ridge } 295 $$

**长 prefill 能压到算力极限**——此时每 token 时间之比 ≈ ridge，**和复用率无关了**（已经撞到算力天花板）。

**统一公式**：

$$ \text{每 token 时间} \;=\; \max\left(\underbrace{\frac{2P}{\text{bandwidth} \times N}}_{\text{带宽摊薄，随 } N \text{ 改善}},\;\; \underbrace{\frac{2P}{\text{FLOPS}}}_{\text{算力极限，封顶}}\right) $$

- $N$ **小时**：第一项主导（带宽受限）→ **增大 $N$ 线性改善**
- $N$ **大到过平衡点后**：第二项主导（算力受限）→ **再增大 $N$ 也不改善**

**所以准确的说法是**：

> **decode 的"单步延迟"低**（4.18 ms vs 58 ms），**但"每 token 成本"高**。
> 生成 $N$ 个 token 的时间，是处理 $N$ 个 token 输入的 **64～295 倍**（倍数取决于 prefill 落在哪个区间）。

### ❌ 误区 4：attention 是 prefill 的瓶颈

**事实**：**prefill 的大头是线性层**（QKV projection、FFN），它们是"权重 × N 个 token"的高复用大矩阵乘（$I \approx 682$）。

**attention 是 prefill 内部偏低的那一块**（未融合时 $I$ 上限只有 $d/2 = 64$，见 03 章 4.6.3）。

$$ \text{所以 FlashAttention 的价值主要体现在 attention 这一块} \quad\ne\quad \text{attention 是整体瓶颈} $$

### ❌ 误区 5：attention 的算术强度 62，说明"序列再长点就好了"

**事实**：**未融合 attention 的算术强度有上限**。

$$ I(N) = \frac{4N^2 d}{2(4Nd + 4N^2)} \;\xrightarrow{\;N\to\infty\;}\; \frac{d}{2} $$

因为**流量和运算都随 $N^2$ 增长，$N$ 被约掉了**：

| $N$ | 未融合 $I$ |
|---|---|
| 4096 | 62.1 |
| 32768 | 63.8 |
| $\infty$ | $\to 64$ **（$= d/2$）** |

**$64 < 295$ ⇒ 未融合 attention 在任何序列长度上都是带宽受限。** 瓶颈不是"序列太长"，**是这种实现方式本身**。

**融合后**（不落 S/P 中间矩阵）才变成 $I = N/2$，随长度增长，$N > 591$ 才翻过分界线——**这是 FlashAttention 存在的量化理由**。

### ❌ 误区 6：KV cache 是为了省显存

**事实**：**KV cache 是为了省计算**。

$$ \text{无 cache：} O(N^3 d/3) \quad\to\quad \text{有 cache：} O(N^2 d/2) \quad\Rightarrow\quad \mathbf{2731 \text{ 倍}（N=4096）} $$

**显存是它的代价**，而且这个代价后来变成了**大问题**（07 章的 KV cache 分级存储、量化、卸载，全都在处理这个代价）。

## 11. 自测（先自己答，再看答案）

**Q1**：prefill 和 decode 用的权重是同一份吗？为什么要分两个名字？

<details>
<summary>答案</summary>

**同一份权重，同一个 `forward` 函数**。分两个名字是因为**工程上要区别对待**（瓶颈不同、指标不同、优化手段不同、可以拆到不同硬件），**不是因为模型上是两个东西**。

</details>

---

**Q2**：为什么说"输入的并行性"不是分两段的根本原因？

<details>
<summary>答案</summary>

因为输入**也可以**串行喂（功能上完全正确）。分段的根本原因是**输出必须串行**（自回归的因果依赖）。prefill 的本质是**把 N 次本该串行的前向合并成 1 次**（合批），目的是**提高权重复用率**，而不是"因为输入必须并行"。

</details>

---

**Q3**：一个 $4096 \times 4096$ 的 FP16 权重，decode 和 prefill 各搬多少？

<details>
<summary>答案</summary>

**都是 32 MiB**——完全一样。**差别不在搬了多少，而在搬完之后被用了几次**：decode 用 1 次，prefill（1024 token）用 1024 次。

</details>

---

**Q4**：H100 的 ridge 是 295 ops/byte。7B FP16 模型在什么条件下变成算力受限？

<details>
<summary>答案</summary>

**约 297 个 token**（精确算 296.6；近似公式 $I \approx N$ 给出 295）。

因为 FP16 下"每个参数 2 字节"和"每 token 每参数 2 FLOP"正好抵消，得到 $I \approx N$。

**推论**：
- 输入 64 token 的 prefill **还是带宽受限**（$I = 63.9$）
- decode 要 batch ≈ 300 才能翻过去（实际很少开这么大）
- **量化把这个数降到 148（FP8）/ 74（INT4）**

</details>

---

**Q5**：为什么投机解码不改善 TTFT？

<details>
<summary>答案</summary>

**TTFT 由 prefill 决定，而投机解码作用在 decode 阶段。** 它是"吐字快"的手段，不是"首字快"的手段。

这是"**两阶段纪律**"的典型应用：**先看指标定位阶段，再选手段**，否则容易白干。

</details>

---

**Q6**：为什么说未融合 attention 的 62 是"上限"而不是"中间值"？

<details>
<summary>答案</summary>

因为它的算术强度**收敛到常数** $d/2$（流量与运算都随 $N^2$ 增长，$N$ 约掉了）。$d = 128$ 时上限是 64。

$64 < 295$ ⇒ **无论序列多长都是带宽受限**。不是"再长点就好了"。

FlashAttention 砍掉 $N^2$ 中间矩阵的往返后变成 $I = N/2$，**才是随长度增长的**，$N > 591$ 时翻过分界线。

</details>

---

**Q7**：长上下文时，decode 的访存结构会怎么变？

<details>
<summary>答案</summary>

$$ \text{每步访存} = \underbrace{2P}_{\text{权重，恒定}} + \underbrace{2 L n_{kv} d_{head} \cdot 2 \cdot N}_{\text{KV，线性增长}} $$

- **短上下文**（几千 token）：KV 只占 4% 左右，**权重主导** → 优化权重（量化）收益最大
- **长上下文**（十万 token）：KV 与权重等量甚至更多 → **优化 KV** 收益最大

**7B 的交叉点 ≈ 10.7 万 token；70B ≈ 42.7 万 token。**

</details>

### 12.2 真实测量：把纸面复算变成真尺子

⚠️ **上面那些脚本全是「纸面复算」**——它们算的是**公式的输出**，不是**硬件的表现**。

$$ \boxed{\text{纸面复算只能验证「我的推理没错」；要验证「理论是否吻合现实」必须实测}} $$

```bash
python3 measure_ridge.py             # 完整实测（256 MiB 数组）
python3 measure_ridge.py --quick     # 快速版（64 MiB，适合共享机器）
python3 measure_ridge.py --compare   # 只看各代硬件对照表
python3 measure_ridge.py --threads 1 # 限制单线程，看 OpenMP 收益
```

**它测三件事**：

| 测什么 | 怎么测 | 为什么必须这么测 |
|---|---|---|
| **内存带宽** | 大数组 `copyto` / `add` / in-place | 数组必须**远大于 L3**，否则测到的是 cache 带宽（**能虚高 10 倍**） |
| **FP32 算力** | 方阵乘法尺寸扫描，取峰值 | 小矩阵受 cache 与线程启动限制而偏低 |
| **ridge** | 算力 ÷ 带宽 | —— |

#### 本机实测结果（i9-14900K / 32 线程 / numpy 2.2.6）

| 项 | 值 |
|---|---|
| 带宽 | **50.8 GB/s** |
| FP32 算力 | **1546 GFLOPS**（2048×2048 峰值） |
| **ridge** | **30.4 ops/byte** |

**尺寸扫描的真实形态**（这不是噪声，是物理）：

| 矩阵尺寸 | GFLOPS | 说明 |
|---|---|---|
| 256 | 782 | 太小：线程启动开销占比高 |
| 512 | 1213 | |
| 1024 | 1437 | |
| **2048** | **1546** | ← 峰值 |
| 3072 | 1288 | 太大：开始被内存带宽拖累 |

$$ \text{这张表本身就是 roofline 的微型演示：太小的矩阵喂不饱计算单元，太大的矩阵喂不上数据} $$

#### 一个反直觉但正确的发现

$$\text{本机 ridge（FP32）} = 30 \quad > \quad \text{H100 ridge（FP32）} = 20$$

**CPU 的 ridge 竟然比 H100 高？**

| 硬件 | 精度 | 算力 | 带宽 | ridge |
|---|---|---|---|---|
| 本机（i9-14900K） | FP32 | 1546 GFLOPS | 50.8 GB/s | **30.4** |
| H100 | FP32 | 67 TFLOPS | 3350 GB/s | **20.0** |
| H100 | FP16（TC） | 989 TFLOPS | 3350 GB/s | **295.2** |
| H100 | FP8（TC） | 1979 TFLOPS | 3350 GB/s | **590.7** |

**原因不是 CPU 强**，而是：

$$ \text{GPU 用 Tensor Core 时算力暴涨 15\text{~}60 倍，但带宽只涨了几倍} \;\Longrightarrow\; \text{这就是「内存墙」} $$

$$ \boxed{\text{GPU 的高 ridge 来自专用矩阵单元，不是来自「带宽小」}} $$

$$ \boxed{\text{所以对比 ridge 时必须标明精度口径，跨精度比是错的}} $$

#### 从实测能推出的两个结论

| 结论 | 计算 | 结果 |
|---|---|---|
| **本机跑 7B 模型 decode 的上限** | $14\ \text{GB} \div 50.8\ \text{GB/s}$ | **约 3.8 token/s** |
| **本机 prefill 的分界点** | $\approx$ ridge（用 $I \approx N$） | **约 30 个 token** |

$$ \text{H100 要 295 个 token 才翻到算力受限侧，本机只要 30 个} $$

$$ \Longrightarrow \quad \boxed{\text{在 CPU 上做 prefill，几乎总是算力受限}} $$

> 💡 **这个数字对你的意义**：你在 T41/Hexagon 上做算子时，**你的板子 ridge 是多少？**
> 换算出它的分界点，就能判断"这个模型在这块板子上是算力受限还是带宽受限"——
> 这比经验判断可靠得多。`measure_ridge.py --custom` 那类参数就是为这个准备的。

#### ⚠️ 实测踩到的四个坑（这段最有价值）

| 坑 | 现象 | 对策 |
|---|---|---|
| **冷启动失真** | 第一次跑，全部数字偏低几十倍 | **跑两遍，用第二遍的数** |
| **warmup 不够** | 同一矩阵尺寸第一轮仍慢 30%~100% | warmup 3 次 + 取多次最优 |
| **数组太小** | 测到 cache 带宽，虚高 10 倍 | 数组远大于 L3（默认 256 MiB） |
| **写分配** | 多流读写模式表观带宽偏低 | 正常现象（实际流量比理论多一份 N） |

**最震撼的是第一行**：我第一次跑脚本时 512×512 只有 **17.6 GFLOPS**，重跑后是 **1213 GFLOPS**——**差 69 倍**。原因仅仅是 OpenBLAS 首次遇到该形状要做 kernel 选择。

$$ \boxed{\text{实测的第一次结果往往不可信 —— 这是实测与纸面复算最大的区别}} $$

**同理**：`measure_ridge.py` 在自己的"诚实声明"里写明了这些坑，**读任何 benchmark 数据时都要先问"测了几遍、warmup 了吗、数组够大吗"**。

## 13. 一页速览

```
一次请求
  │
  ├─ 阶段 0：tokenize（不需要神经网络）
  │
  ├─ 【Prefill】跑 1 次        输入 N 个 token → X[N, d]
  │    瓶颈：算力（N > ~300 时）
  │    产出：第 1 个输出 token + KV cache（写入）
  │    决定：TTFT
  │    为什么快：N 个 token 共用一次权重搬运 → 复用率 N
  │
  └─ 【Decode】跑 N_out-1 次   输入 1 个 token → x[1, d]
       瓶颈：带宽（几乎总是）
       产出：之后每个输出 token，KV cache 读取 + 追加
       决定：TPOT / 吞吐
       为什么慢：权重每个 token 都要重搬一遍 → 复用率 1

两个阶段：
    ✅ 同一套权重
    ✅ 同一个 forward 函数
    ✅ 代码路径相同
    ❌ 不是两个模型
    ⚠️ 唯一差别：一次喂 N 个 token 还是 1 个 token

一句话：
    复用率 = token 数（FP16 下）
    I ≈ N；H100 ridge = 295 → 约 300 个 token 是分界线
```
