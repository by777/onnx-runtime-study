## 三、常量折叠（C1/C2）

### 3.1 什么是折叠

**编译期就把常量运算算完**，运行时不用算。

```
优化前:  %2 = addi(const2, const3)    优化后:  %c5 = constant 5
```

### 3.2 折叠的场景（C2 实验）

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 常量加 | `addi(7,5)` | `12` |
| 常量乘 | `muli(7,5)` | `35` |
| 常量减 | `subi(35,12)` | `23` |
| **加 0 恒等** | `addi(x,0)` | `x` |

**加 0 恒等是"规范化"**：不只折叠，还识别数学恒等（`x+0=x`），统一成最简形式。

### 3.3 为什么叫"canonicalize"（规范化）

它做三类事：
1. **折叠**：常量运算算完（`2+3→5`）
2. **化简**：恒等化简（`x+0→x`）
3. **规范化**：等价写法统一（同一种意思用同一种写法）

所以 `canonicalize` 是"一组小优化的集合"，不是单个优化。

## 四、死代码消除 DCE（C3）

### 4.1 什么是死代码

**算出来但没人用的值**。

```
%dead = muli(1,2)   // 算完没人用 → 死
return %3           // 只返回活的值
```

### 4.2 怎么判断死活

编译器从 `return` **反向追踪**：
- `return %2` 需要 `%2` → `%2` 活的
- `%2` 需要 `%0`/`%1` → 它们活的
- `%dead1`/`%dead2`/`%dead3` 没被任何活值用 → 死的 → 删

**关键**：依赖死代码的也是死的（`dead3` 依赖 `dead1`/`dead2`，跟着删）。

### 4.3 对应

TVM 的 `DeadCodeElimination` pass、ORT 的图优化，同原理。

## 五、CSE 公共子表达式消除（C4b）

### 5.1 什么是 CSE

**两个完全相同的计算，只算一次**。

```
优化前:  %a = muli(3,4)    优化后:  %0 = muli(3,4)
        %b = muli(3,4)              %1 = addi(%0, %0)
        %c = addi(%a, %b)
```

`3*4` 算两次 → 合并成一次，两个地方用同一个 `%0`。

### 5.2 为什么能合并

因为 **SSA 值不可变**——`%0` 的值永远不变，所以两处用 `%0` 保证得到同样结果。这就是 SSA 设计的好处（B 组讲过）。

## 六、Pass 管线（C4/C4b）

### 6.1 为什么需要多个 pass

单个 pass 只干一件小事。**多个 pass 串起来才能干大事**：

```
C4b:  两个 3*4 → [CSE] → 一个 3*4 → [canonicalize] → 24
```

每个 pass 在前一个 pass 的结果上继续工作，像流水线工位。

### 6.2 管线语法

```bash
--pass-pipeline="builtin.module(func.func(cse,canonicalize))"
```

| 部分 | 含义 |
|---|---|
| `builtin.module(...)` | 作用域：整个模块 |
| `func.func(...)` | 对每个函数内部 |
| `cse,canonicalize` | 依次跑这两个 pass |

### 6.3 观察工具（最重要）

```bash
--mlir-print-ir-after-all     # 每个 pass 跑完打印一次 IR（看每步变化）
--mlir-pass-statistics        # 每个 pass 的统计信息
```

`--mlir-print-ir-after-all` 是**调试编译器最重要的工具**——能亲眼看到"3*4 两次 → CSE 合并 → 折叠成 24"的全过程。对应 TVM 的 `--print-ir-after=pass`。

## 七、这些优化是自动的吗？

**问**：常量折叠/DCE/CSE 看起来都是编译器会做的优化，是自动的吗？

**答**：是，但要分两层理解。

### 7.1 优化执行是自动的

你写 `addi(const2, const3)`，跑 `canonicalize` 就自动折成 5——不需要你告诉它"请折叠"。和 GCC 的 `-O2` 一样，优化自动执行。

### 7.2 优化策略是人工的

编译器**不是永远优化**——要显式指定跑哪些 pass：

| | GCC/Clang | MLIR |
|---|---|---|
| 优化过程 | **黑盒**（`-O2` 一下完事，看不到中间） | **白盒**（每 pass 跑完能看到 IR） |
| 能控制吗 | 只能选 `-O0/-O1/-O2/-O3` 套餐 | **精确到每个 pass**，自选顺序、自写 pass |
| 优化对象 | C 语言 | **任何方言**（包括你自己的 NPU 方言） |

### 7.3 为什么这对工具链岗位重要

- GCC 里优化是"买套餐"（-O2 打包好），你不能改
- MLIR 里优化是"点菜"（每个 pass 单独一道），你能定制、能自己加菜
- **工具链工程师的价值**：给自家 NPU 写一个 `npu-fusion` pass（把 conv+relu 融合），这是 GCC 给不了的

### 7.4 一句话总结

> **优化执行是自动的（pass 自动变换图），但优化策略是人工设计的（人决定跑哪些 pass、什么顺序、甚至自己写 pass）。MLIR 把优化的"决策权"从编译器手里交还给编译器工程师。**

## 九、小结

| pass | 干什么 | 一句话 |
|---|---|---|
| `canonicalize` | 折叠+化简+规范化 | 让图最简 |
| `cse` | 相同计算只算一次 | 去重 |
| 管线 | 多个 pass 串起来 | 流水线 |
| `--mlir-print-ir-after-all` | 每步打印 IR | 看透编译器 |
